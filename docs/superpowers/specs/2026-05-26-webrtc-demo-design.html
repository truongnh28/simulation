1. Phân tích WebRTC — Protocol Deep Dive

1.1 WebRTC là gì và tại sao nó phức tạp

WebRTC (Web Real-Time Communication) là tập hợp các API và protocol cho phép trình duyệt trao đổi audio, video, và data trực tiếp với nhau — không qua server trung gian cho media. Đây là điểm cốt lõi: server chỉ cần thiết cho giai đoạn "giới thiệu" ban đầu (signaling), còn media đi thẳng peer-to-peer.

Sự phức tạp xuất phát từ 3 vấn đề thực tế: NAT traversal (hầu hết thiết bị nằm sau NAT, không có IP công khai), bảo mật bắt buộc (DTLS + SRTP không thể tắt), và codec negotiation (mỗi browser hỗ trợ codec khác nhau).

1.2 Stack protocol đầy đủ

Application
JavaScript WebRTC API — RTCPeerConnection, RTCDataChannel, MediaStream
Media / Data
SRTP — mã hóa audio/video  |  SCTP over DTLS — DataChannel (ordered/unordered, reliable/unreliable)
Security
DTLS 1.2/1.3 — TLS-over-UDP, thiết lập key exchange, xác thực certificate bằng fingerprint trong SDP
Transport
ICE — chọn đường đi tốt nhất  |  STUN — discover public IP  |  TURN — relay fallback
Network
UDP (preferred) hoặc TCP fallback  |  IPv4 / IPv6

1.3 Signaling — thứ WebRTC KHÔNG định nghĩa

WebRTC chủ động không định nghĩa cơ chế signaling. Bạn có thể dùng WebSocket, HTTP polling, XMPP, carrier pigeon — miễn là 2 peer trao đổi được SDP và ICE candidates với nhau.

Signaling chỉ cần truyền 2 loại thông tin:

  • SDP Offer/Answer — mô tả capability của mỗi peer (codec, IP, port)
  • ICE Candidates — danh sách địa chỉ mạng có thể dùng để kết nối
Sau khi signaling hoàn tất và ICE connected, signaling server có thể đóng hoàn toàn — media flow trực tiếp giữa 2 peer.

1.4 SDP — Session Description Protocol

SDP là định dạng text mô tả "tôi có thể làm gì" — không phải protocol truyền tải, chỉ là metadata. Một SDP offer thực tế:

v=0
o=- 8447722553217982387 2 IN IP4 127.0.0.1
s=-
t=0 0
a=group:BUNDLE 0 1          ← gộp audio + video vào 1 kết nối ICE
a=extmap-allow-mixed
m=video 9 UDP/TLS/RTP/SAVPF 96 97 98   ← media section: video, port 9 (ICE override)
c=IN IP4 0.0.0.0
a=rtcp:9 IN IP4 0.0.0.0
a=ice-ufrag:xKkP             ← ICE username fragment (authentication)
a=ice-pwd:bZ4tM...           ← ICE password (authentication)
a=ice-options:trickle        ← hỗ trợ trickle ICE
a=fingerprint:sha-256 4A:... ← DTLS certificate hash (xác thực peer)
a=setup:actpass              ← ai sẽ làm DTLS client/server
a=mid:0                      ← media ID cho BUNDLE
a=sendrecv                   ← direction: gửi và nhận
a=rtpmap:96 VP8/90000        ← codec: VP8, clock rate 90kHz
a=rtpmap:97 rtx/90000        ← RTX: retransmission cho VP8
a=rtpmap:98 H264/90000       ← codec: H264
a=fmtp:98 level-asymmetry-allowed=1;packetization-mode=1;profile-level-id=42e01f
a=ssrc:3421 cname:abc123     ← SSRC: định danh stream

SDP Answer trả về subset của những gì offer đề xuất — codec nào được chọn, direction thực tế là gì.

1.5 ICE — Interactive Connectivity Establishment

ICE giải quyết bài toán: "làm sao 2 peer sau NAT kết nối được với nhau?" Quá trình gồm 3 giai đoạn:

Giai đoạn 1: Candidate Gathering

Mỗi peer thu thập tất cả địa chỉ có thể kết nối:

  • host — IP local trực tiếp (192.168.1.5:52341). Nhanh nhất, chỉ dùng được trong LAN.
  • srflx (Server Reflexive) — IP công khai được STUN server reflect lại (203.0.113.1:48291). Vượt được Full Cone NAT.
  • relay — địa chỉ TURN server sẽ relay thay (turn-server:3478). Luôn hoạt động nhưng tốn băng thông và latency cao nhất.

Giai đoạn 2: Connectivity Checks (STUN Binding Requests)

Hai peer gửi STUN requests cho tất cả candidate pairs của nhau theo thứ tự ưu tiên. Mỗi pair được check theo cả 2 chiều. Pair đầu tiên succeed là "valid pair".

Giai đoạn 3: Nomination

Controlling peer (thường là bên tạo offer) chọn candidate pair tốt nhất từ các valid pairs. Sau khi nominated, traffic chuyển sang pair đó.

Trickle ICE: Thay vì chờ gather xong hết mới gửi, candidates được gửi ngay khi tìm thấy (trickling). Giảm latency kết nối đáng kể — browser hiện đại đều dùng trickle ICE mặc định.

1.6 NAT Types và khả năng traversal

NAT TypeMô tảICE có vượt được?
Full ConeBất kỳ ai biết public IP:port đều kết nối đượcCó — dùng srflx
Restricted ConeChỉ IP đã từng liên lạc mới vào đượcCó — ICE tạo "hole" trước
Port RestrictedChỉ IP+port đã từng liên lạc mới vào đượcCó — ICE tạo "hole" trước
SymmetricMỗi đích khác nhau nhận được port khác nhauKhó — cần TURN relay
Symmetric NAT là nguyên nhân chính khiến ICE failed. Doanh nghiệp và carrier-grade NAT thường dùng Symmetric NAT — đây là lý do hệ thống production luôn cần TURN server.

1.7 DTLS Handshake

Sau khi ICE tìm được candidate pair, DTLS handshake thiết lập channel mã hóa. DTLS là TLS chạy trên UDP (thay vì TCP).

Peer A (client)          Peer B (server)
     |                        |
     |--- ClientHello -------→|
     |←-- ServerHello --------|
     |←-- Certificate --------|   ← browser tự tạo self-signed cert
     |←-- ServerHelloDone ----|
     |--- ClientKeyExchange --→|
     |--- ChangeCipherSpec ---→|
     |--- Finished -----------→|
     |←-- ChangeCipherSpec ----|
     |←-- Finished ------------|
     |                        |
     |== DTLS channel ready ==|

Certificate được xác thực không phải qua CA mà qua fingerprint trong SDP — đây là lý do SDP phải được truyền qua kênh an toàn (signaling server).

1.8 SRTP — Secure RTP

Media (audio/video) không đi qua DTLS channel — thay vào đó, key từ DTLS handshake được dùng để thiết lập SRTP (Secure Real-time Transport Protocol) riêng biệt. Lý do: RTP cần cấu trúc packet tối ưu cho media, DTLS overhead quá lớn cho từng frame video.

SRTP cung cấp: mã hóa payload, xác thực integrity, và bảo vệ replay attack. Keys được derive từ DTLS qua cơ chế DTLS-SRTP (RFC 5764).

1.9 Codec Negotiation

CodecLoạiBrowser supportĐặc điểm
VP8VideoChrome, Firefox, SafariOpen source, baseline chất lượng tốt
VP9VideoChrome, FirefoxNén tốt hơn VP8 ~50%, Safari hạn chế
H264VideoChrome, Firefox, SafariHardware acceleration rộng rãi, phổ biến nhất cho drone/camera
H265/HEVCVideoSafari (hạn chế)Nén tốt nhất nhưng WebRTC support yếu
OpusAudioTất cảBắt buộc trong WebRTC, adaptive bitrate 6-510 kbps

Quá trình negotiation: Offerer liệt kê tất cả codec hỗ trợ theo thứ tự ưu tiên. Answerer chọn codec đầu tiên mà cả hai đều hỗ trợ. Drone streaming nên ưu tiên H264 vì hầu hết camera hardware có H264 encoder sẵn.

1.10 DataChannel — SCTP over DTLS

DataChannel dùng SCTP (Stream Control Transmission Protocol) chạy trên DTLS channel — không liên quan đến RTP. SCTP cung cấp tính năng mà TCP và UDP thiếu:

Tính năngTCPUDPSCTP (DataChannel)
Ordered deliveryLuôn cóKhôngTùy chọn
Reliable deliveryLuôn cóKhôngTùy chọn
Multi-streamKhôngKhôngCó — nhiều channels độc lập
Head-of-line blockingCóKhôngKhông (giữa streams)
Partial reliabilityKhôngKhôngCó — maxRetransmits / maxPacketLifeTime
Game và telemetry thường dùng ordered: false, maxRetransmits: 0 — nhanh như UDP nhưng vẫn qua WebRTC infrastructure. File transfer cần ordered: true và reliable.

1.11 getStats() — Connection Diagnostics API

RTCPeerConnection.getStats() trả về hàng chục loại report. Những metric quan trọng nhất:

Report TypeKey Metrics
inbound-rtpbytesReceived, packetsLost, jitter, framesDecoded, framesPerSecond
outbound-rtpbytesSent, packetsSent, framesSent, qualityLimitationReason
candidate-paircurrentRoundTripTime, availableOutgoingBitrate, bytesDiscardedOnSend
local-candidatecandidateType (host/srflx/relay), ip, port, protocol
codecmimeType (video/H264), clockRate, sdpFmtpLine

Tính bitrate thực tế: lấy bytesReceived ở 2 thời điểm liên tiếp, chia cho khoảng thời gian giữa 2 lần đo.

Annotation System

Mỗi WebRTC event được log với 3 lớp:

Raw
onicecandidate: {candidate: "candidate:1 1 UDP 2122... 192.168.1.5 52341 typ host"}
Giải thích
ICE đang thu thập địa chỉ mạng. typ host = địa chỉ LAN trực tiếp của máy.
Tại sao
Browser thử tất cả đường đi có thể (host → srflx → relay) trước khi chọn đường tốt nhất qua connectivity checks.

SDP Inspection Panel

Raw SDP offer/answer hiển thị toàn bộ, các field được highlight và annotate:

  • a=ice-ufrag / a=ice-pwd — credentials cho ICE authentication
  • a=fingerprint:sha-256 — hash của DTLS certificate, xác thực peer identity
  • a=setup:actpass — negotiate ai làm DTLS client, ai làm server
  • m=video / m=audio — mỗi block mô tả 1 media track
  • a=rtpmap — mapping giữa payload type number và codec name
  • a=sendrecv / a=sendonly / a=recvonly — direction của stream

4. Phase 2 Drone Ground Station

Signaling Flow

[Drone Tab]        [server.js WebSocket]      [Ground Station Tab]
     |                      |                           |
     |-- connect WS -------→|←-------- connect WS ------|
     |-- {type:"offer", sdp}→|                          |
     |                       |-- relay offer -----------→|
     |                       |←-- {type:"answer", sdp}--|
     |←-- relay answer ------|                          |
     |-- {type:"ice", ...} --→|-- relay ICE ------------→|
     |                       |←-- {type:"ice", ...} ----|
     |←-- relay ICE ---------|                          |
     |←============= one-way video stream ==============|
     |←======= DataChannel: chat + file transfer =======|

server.js — Signaling Relay

  • Node.js built-in http module serve static HTML — không dùng Express
  • ws@8 xử lý WebSocket — lightweight, readable code
  • Logic đơn giản: 2 clients, message từ client A forward sang client B và ngược lại
  • Không có message queuing, không có rooms, không có auth

drone.html — Video Sender

  • Source selector:
    • Webcam: getUserMedia({ video: true, audio: true })
    • Video file: <input type="file"> → URL.createObjectURL() → HTMLVideoElement.captureStream()
  • RTCPeerConnection: addTrack() media tracks, tạo offer, gather ICE
  • Uplink stats: bitrate gửi (KB/s), resolution, framerate, ICE candidate type đang dùng
  • DataChannel initiator: mở chat-channel (hai chiều) và file-channel (drone → GS)

ground-station.html — Video Receiver

  • Video display: ontrack event → set video.srcObject = event.streams[0]
  • Text chat: gửi/nhận qua chat-channel
  • File transfer: reassemble chunks từ file-channel, tạo Blob, trigger download
  • Stats panel (poll 1s qua getStats()): codec, resolution, fps, RTT, packet loss %, jitter, ICE candidate pair

DataChannels

ChannelOrderedReliablePayloadDirection
chatCóCó UTF-8 JSON {from, text, ts}Hai chiều
fileCóCó ArrayBuffer chunks 16 KB + metadata JSONDrone → GS

File Transfer Protocol

  1. Drone gửi {type:"file-start", name, size, totalChunks}
  2. Drone gửi totalChunks lần ArrayBuffer (mỗi chunk ≤ 16 KB)
  3. Drone gửi {type:"file-end"}
  4. GS reassemble → new Blob(chunks) → URL.createObjectURL() → trigger download

STUN / TURN Config

{ iceServers: [{ urls: "stun:stun.l.google.com:19302" }] }
