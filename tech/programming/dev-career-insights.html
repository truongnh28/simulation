🚀 Dev → Ops → Dev

12 bài học vận hành production từ kỹ sư đã đi qua cả con đường phát triển phần mềm và vận hành hệ thống — những insight chỉ có thể học được từ thực chiến

1. Hành Trình Dev → Ops → Dev

Có một vòng đời thú vị trong sự nghiệp kỹ thuật: bắt đầu là Developer viết code, sau đó chuyển sang Ops chịu trách nhiệm vận hành, rồi quay lại vai trò Development nhưng với perspective hoàn toàn khác. Những ai đã đi qua vòng này thường trở thành những kỹ sư giỏi nhất — họ viết code với sự hiểu biết rằng code sẽ phải chạy trong production, fail theo những cách unexpected, và được debug lúc 3 giờ sáng.

2. 12 Bài Học Từ Production

BÀI HỌC 01
Monitoring Không Phải Là Thứ Thêm Vào Sau

Developer thường build feature xong rồi mới nghĩ đến monitoring. Ops person học rất nhanh rằng đây là sai lầm chết người. Khi system fail lúc 3 giờ sáng và không có metric gì, bạn đang blind. Observability phải là first-class citizen từ ngày đầu, không phải afterthought.

Ba trụ cột của observability: Metrics (số liệu về hệ thống), Logs (events có cấu trúc), Traces (luồng request qua các services). Thiếu bất kỳ cái nào, bạn đang debug với một tay bị buộc sau lưng.

→ Khi viết code: thiết kế metrics cùng với API. Instrumentation code nên dễ viết hơn business logic.
BÀI HỌC 02
Logs Có Cấu Trúc — Không Phải Printf

log.Printf("Error processing user %d: %s", userID, err) là fine khi debug locally. Nhưng trong production với 100K requests/second và 50 server nodes, bạn cần query logs như database. Structured logging (JSON) cho phép filter: log.level=ERROR AND user_id=123 AND service=checkout. Unstructured text logging làm điều đó bất khả thi.

// Bad: unstructured
log.Printf("Failed to process order %s for user %d, error: %v", orderID, userID, err)

// Good: structured
log.WithFields(log.Fields{
    "order_id": orderID,
    "user_id":  userID,
    "error":    err,
    "duration": elapsed,
}).Error("order_processing_failed")
→ Mọi log entry nên có: timestamp, level, service name, trace_id, và relevant context fields. Không bao giờ log sensitive data (PII, passwords, tokens).
BÀI HỌC 03
Timeout Ở Mọi Nơi — Không Có Default Là Vô Hạn

Một trong những bug phổ biến nhất trong distributed systems: gọi external service mà không có timeout. Service đó bị slow, thread của bạn block vô thời hạn, thread pool cạn, toàn bộ service hang. Cascading failure từ một dependency chậm — thảm họa kinh điển.

Mọi outbound call đều cần: connection timeout (mất bao lâu để connect), read timeout (mất bao lâu để nhận response), overall timeout (tổng request không vượt quá X giây). Circuit breaker thêm lớp bảo vệ khi dependency fail hoàn toàn.

// Never do this:
resp, err := http.Get(url)  // No timeout!

// Always do this:
client := &http.Client{
    Timeout: 3 * time.Second,  // overall timeout
    Transport: &http.Transport{
        DialTimeout: 1 * time.Second,     // connection timeout
        ResponseHeaderTimeout: 2 * time.Second,
    },
}
→ Default timeout cho mọi external call: 1s connection, 5s read, 10s overall. Điều chỉnh dựa trên SLA thực tế. Không bao giờ để vô hạn.
BÀI HỌC 04
Graceful Shutdown — Không Kill -9 Blindly

Khi deploy version mới, process cũ phải shutdown. kill -9 (SIGKILL) terminate ngay lập tức — in-flight requests bị drop, database connections bị force-closed, background jobs bị interrupt giữa chừng. Graceful shutdown (SIGTERM) cho phép process finish requests đang xử lý trước khi exit.

Mọi service đều nên implement: nhận SIGTERM → stop accepting new requests → wait for in-flight requests (với timeout, e.g., 30s) → close connections → exit. Kubernetes drain cũng cần graceful shutdown để zero-downtime deployment thực sự là zero-downtime.

→ Implement SIGTERM handler trong mọi service. Test shutdown behavior trong staging. Đừng chỉ test happy path.
BÀI HỌC 05
Config Thay Đổi Là Risk — Không Kém Gì Code Deploy

Nhiều người nghĩ "chỉ thay đổi config, không phải code, an toàn hơn deploy". Sai. Một số outage lớn nhất đến từ config change. Timeout value sai → cascading failure. Feature flag enable nhầm → unexpected code path chạy. Database connection pool size thay đổi → connection exhaustion.

Config changes nên được xử lý như code: code review, staging test, canary rollout, easy rollback. Config drift giữa production và staging là nguồn gốc của "works on staging, fails in production" syndrome.

→ Tất cả config thay đổi qua version control. Config khác nhau giữa environments phải được document rõ ràng. Có mechanism rollback nhanh.
BÀI HỌC 06
Runbook Phải Được Test — Không Phải Viết Rồi Quên

Mọi service đều nên có runbook: tài liệu mô tả cách respond khi có incident. "Restart service X", "Rollback database Y", "Scale up Z nodes". Vấn đề: runbooks thường được viết sau incident đầu tiên và sau đó không bao giờ được test lại.

Khi incident thực sự xảy ra lúc 3 giờ sáng, bạn follow runbook step-by-step. Nếu runbook outdated (service đã được refactored, command đã thay đổi), bạn lãng phí thời gian quý báu để debug tại sao step 3 không work. Chaos Engineering (Netflix's approach) là test runbooks trong production proactively.

→ Quarterly runbook review. Mỗi incident kết thúc bằng post-mortem và runbook update. Junior engineers on-call trước với senior backup.
BÀI HỌC 07
Database Migration Là Bước Nguy Hiểm Nhất Trong Deploy

Code có thể rollback trong seconds. Database schema migration không thể (dễ dàng). Thêm column: safe. Xóa column: nguy hiểm nếu old code vẫn đang chạy. Rename column: thảm họa với zero-downtime deploy. Mọi migration phải backward-compatible với version code cũ ít nhất một deploy cycle.

Pattern an toàn cho rename column: (1) Add new column, (2) Deploy code write cả hai columns, (3) Backfill data sang new column, (4) Deploy code chỉ read new column, (5) Drop old column. 5 steps thay vì 1 step "rename" — nhưng zero downtime và rollback được ở mọi bước.

→ Mọi migration phải có rollback plan. Test migration trên production-size dataset trong staging. Never rename or drop columns without the multi-step process.
BÀI HỌC 08
Idempotency Không Phải Option — Là Requirement

Trong distributed systems, mọi operation có thể được thực hiện nhiều hơn một lần — network retry, message queue redelivery, client timeout và retry. Nếu "charge user $100" không idempotent, user bị charge hai lần khi network timeout sau khi charge thành công nhưng trước khi response đến client.

Idempotency key: mỗi request có unique ID. Server check "đã xử lý ID này chưa?" trước khi thực hiện. Nếu rồi, return cached result. Nếu chưa, xử lý và lưu result. Idempotency keys nên có TTL (vài ngày đến vài tuần, tùy business logic).

// Idempotent charge endpoint:
POST /charges
{
  "amount": 100,
  "currency": "USD",
  "idempotency_key": "order-123-charge-attempt-1"  // unique per attempt
}

// Server:
if exists(idempotency_key): return cached_result  // no double charge
else: process_charge(); store_result(idempotency_key, result)
→ Payment, inventory decrement, email send — tất cả phải idempotent. Thiết kế idempotency từ ngày đầu, không phải sau khi bug xuất hiện production.
BÀI HỌC 09
SLA, SLO, Error Budget — Đừng Nhầm Lẫn

SLA (Service Level Agreement): cam kết với khách hàng, vi phạm có hậu quả pháp lý/tài chính. SLO (Service Level Objective): mục tiêu nội bộ, thường chặt hơn SLA (để có buffer trước khi vi phạm SLA). Error Budget: lượng downtime/errors được phép trong một period trước khi vi phạm SLO.

Error Budget tạo ra ngôn ngữ chung giữa Dev và Ops: "Chúng ta còn 30% error budget tháng này. Tính năng X có rủi ro cao, nên delay deploy sang tháng sau." Không còn tranh luận chủ quan "có nên deploy không?" — có số liệu rõ ràng.

→ 99.9% SLO = 8.7 giờ downtime/năm. 99.99% = 52 phút/năm. 99.999% = 5 phút/năm. Biết rõ SLO của mình trước khi thiết kế kiến trúc.
BÀI HỌC 10
Không Có "Infrastructure" — Chỉ Có Tradeoffs

Developer nhìn infrastructure như black box: "Cloud lo, tôi chỉ cần push code". Ops person biết rõ: mỗi choice có tradeoffs. Managed service (RDS) vs self-managed (MySQL on EC2): managed service đơn giản hơn, nhưng ít control hơn, đắt hơn, và có limitations. Multi-AZ vs single-AZ: HA cao hơn nhưng latency cao hơn và cost gấp đôi.

Hiểu tradeoffs giúp bạn thiết kế hệ thống đúng cho requirements. "Chúng ta có thể dùng DynamoDB?" cần biết: access patterns là gì, consistency requirements là gì, cần scan/sort gì không? Không có "tốt nhất" — chỉ có "phù hợp nhất cho use case".

→ Mỗi technology decision nên có decision document ghi rõ: options considered, tradeoffs, why this choice, review date. Tránh cargo-culting technology chỉ vì "Netflix dùng".
BÀI HỌC 11
Blameless Post-Mortem: Học Từ Thất Bại

Sau mỗi incident, instinct tự nhiên là tìm người để blame: "Ai deploy cái này?" Blameless post-mortem (Google's model) tiếp cận khác: tìm systemic causes, không individual blame. "Tại sao system cho phép deploy này xảy ra? Tại sao monitoring không catch sớm hơn? Tại sao không có canary?"

Blame culture tạo ra fear culture: người ta không dám thử thứ mới, không thừa nhận mistakes, và không chia sẻ near-misses (mà near-misses là cơ hội học quý báu nhất). Blameless culture tạo ra psychological safety — điều kiện để team thực sự improve.

→ Post-mortem template: Timeline → Root causes → Impact → What went well → What went wrong → Action items. Focus vào systemic fixes, không cá nhân.
BÀI HỌC 12
Production Mindset: Code Sẽ Fail — Thiết Kế Cho Điều Đó

Kỹ sư có Production Mindset viết code với assumption: "code này sẽ fail, câu hỏi là fail như thế nào và hệ thống recover ra sao?" Họ thiết kế: graceful degradation (khi payment service down, vẫn show catalog), circuit breaker (ngừng gọi service đang fail), bulkhead (isolate failure để không spread), retry với exponential backoff.

Sự khác biệt giữa senior và junior engineer không phải là số lượng design patterns biết, mà là khả năng anticipate failure modes. "What happens if this API call returns 503?" "What if database connection pool is exhausted?" "What if this message is processed twice?"

→ Trước mỗi PR: "Nếu external dependency fail, code này làm gì?" Câu trả lời không thể là "không biết" hay "sẽ throw exception". Phải là "graceful fallback / clear error / log + alert".

3. Synthesis: Từ Bài Học Đến Mindset

12 bài học trên không phải là checklist để hoàn thành rồi tick. Chúng là reflection của một mindset: kỹ sư giỏi không chỉ build systems, họ build systems sẵn sàng cho production — có thể monitor được, có thể debug được, có thể rollback được, và có thể fail gracefully.

💜 The Full Stack Engineer vs The Full Cycle Engineer

"Full Stack" thường được hiểu là biết cả frontend và backend. Nhưng "Full Cycle" (Netflix's term) là hiểu biết cả development và operations: viết code, deploy code, monitor code, debug code trong production, và improve code dựa trên production insights. Full Cycle Engineer xây hệ thống tốt hơn vì họ sẽ là người chịu hậu quả khi hệ thống fail. Skin in the game là người thầy tốt nhất.

✅ Áp Dụng Vào Công Việc Hàng Ngày

Không cần làm Ops để có Production Mindset. Hãy tự hỏi trong code review: "Làm sao monitor feature này?" "Nếu có bug trong production, làm sao debug?" "Code này fail thế nào?" Join on-call rotation ít nhất một lần, dù chỉ shadow — bạn sẽ học được nhiều hơn một năm training. Đọc post-mortems của các công ty lớn (Google, AWS, Stripe) — đây là case studies về real-world engineering.

⚠️ Tránh "Ops Theater"

Có dashboard không có nghĩa là observable. Có monitoring không có nghĩa là hiểu system. "Ops theater" là giả vờ sẵn sàng mà không thực sự sẵn sàng: alert quá nhiều nên bị mute, runbook outdated không ai update, on-call rotation mà không có quyền thực sự để fix vấn đề. Thực chất quan trọng hơn hình thức.

4. Kết Luận

Con đường Dev → Ops → Dev không phải là con đường mọi kỹ sư phải đi. Nhưng mentality của nó — hiểu rằng code tồn tại trong production, cần được vận hành, và sẽ fail — là mentality mà mọi kỹ sư phần mềm nên có, bất kể title hay chuyên môn.

Bài học lớn nhất: Software engineering không kết thúc khi code merge. Nó kết thúc khi feature được dùng bởi users, stable trong production, và team hiểu tại sao nó hoạt động — và tại sao đôi khi nó không.
