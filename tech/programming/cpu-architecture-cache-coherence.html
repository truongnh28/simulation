🖥️ Kiến Trúc CPU & Cache Coherence

Superscalar, SMT, Out-of-Order Execution, MESI Protocol, Memory Consistency Model và ứng dụng trong database

1. CPU Hiện Đại: Từ Fetch Đến Retire

CPU hiện đại không thực thi instruction một cách tuần tự. Thay vào đó, chúng dùng pipeline nhiều giai đoạn:

  1. Fetch: Đọc nhiều macro-instructions từ cache vào pipeline
  2. Decode: Chuyển thành micro-ops (uops) đơn giản hơn
  3. Dispatch: Gửi micro-ops đến các Reservation Stations
  4. Execute: Thực thi trên các Functional Units (ALU, FPU, Load/Store)
  5. Retire: Ghi kết quả vào permanent storage (registers/memory)

Super Pipelining

Chia pipeline thành nhiều giai đoạn nhỏ hơn, tăng clock frequency. Nhưng các giai đoạn phụ thuộc nhau (data hazards) gây pipeline stalls.

Superscalar

Thực thi NHIỀU instructions cùng lúc trên các FUs song song (Instruction Level Parallelism). IPC (Instructions Per Cycle) > 1.

2. SMT — Simultaneous MultiThreading

SMT (Intel gọi là HyperThreading) cho phép 1 physical core thực thi 2 threads cùng lúc bằng cách chia sẻ các Functional Units:

  • Không có thread đơn lẻ nào có thể sử dụng hết 100% các FUs của 1 core
  • SMT tận dụng các FU nhàn rỗi này bằng thread khác
  • Kết quả: throughput tăng ~20-30% (không phải 2x) với 2 threads trên 1 core

⚠️ SMT và Database Performance

Với database workload, SMT có thể giúp hoặc hại tùy thuộc vào loại workload. CPU-intensive queries hưởng lợi ít hơn I/O-bound queries. Một số DBA tắt HyperThreading để giảm cache pollution và có predictable latency.

3. Out-of-Order Execution

CPU có thể thực thi instructions theo thứ tự KHÁC với thứ tự trong chương trình, miễn là không vi phạm data dependencies:

// Nguồn code:
a = b + c;   // Instruction 1 (phụ thuộc b, c)
d = e + f;   // Instruction 2 (không phụ thuộc I1)
g = a + d;   // Instruction 3 (phụ thuộc I1 và I2)
// CPU có thể thực thi I1 và I2 song song!

Out-of-Order Execution tăng ILP lên đáng kể nhưng tạo ra Memory Ordering issues — nguồn gốc của nhiều bugs trong concurrent programming.

💡 Cache Line = 64 Bytes

CPU đọc/ghi dữ liệu theo đơn vị Cache Line (64 bytes trên x86). Nếu 2 threads ghi vào 2 variables khác nhau nhưng cùng cache line → FALSE SHARING → hiệu năng giảm mạnh do cache thrashing. Fix: padding các variables đến 64-byte boundary.

5. Cache Coherence — Nhất Quán Cache Giữa Các Core

Khi nhiều cores có L1/L2 cache riêng, làm sao đảm bảo chúng thấy cùng giá trị của cùng biến?

5.1 MESI Protocol

MESI là cache coherence protocol phổ biến nhất (Intel, AMD). Mỗi cache line có thể ở một trong 4 trạng thái:

Trạng tháiÝ nghĩaCó thể đọc?Có thể ghi?
ModifiedChỉ core này có, đã sửa, chưa sync về memory✅✅
ExclusiveChỉ core này có, chưa sửa, đồng bộ với memory✅✅ (→ Modified)
SharedNhiều cores có, chưa sửa✅❌ (phải Invalidate others)
InvalidCache line không hợp lệ❌❌

5.2 Ứng Dụng Thực Tế: False Sharing trong InnoDB

// Vấn đề: global counter bị false sharing
static uint64_t rows_read = 0;  // Nhiều threads tăng counter này

// Mỗi thread write vào rows_read → invalidate cache line của tất cả cores
// → MESI Invalidation storm → hiệu năng giảm 10-50x!

// Giải pháp: per-thread counter với padding
struct alignas(64) PerThreadCounter {
    uint64_t value;
    // Padding để chiếm đúng 1 cache line (64 bytes)
    char padding[64 - sizeof(uint64_t)];
};

✅ G5 Discovery: MySQL 5.6 Tăng 50% Scalability

MySQL team phát hiện srv_n_rows_read++ là global counter gây false sharing nặng. Fix: chuyển sang per-thread counter với cache line padding. Kết quả: Sysbench OLTP RO tăng >50% scalability trên server nhiều core. Đây là ví dụ điển hình về "Mechanical Sympathy".

6. Memory Consistency — Memory Model

Cache Coherence đảm bảo các cores đồng ý với nhau. Memory Consistency định nghĩa: các loads và stores từ các threads khác nhau thấy nhau thế nào?

6.1 Store Buffer và Memory Reordering

Để tăng hiệu năng, CPU dùng Store Buffer: ghi store vào buffer trước khi flush về cache. Điều này có thể gây reordering:

  • StoreLoad reordering: Store chưa flush, Load đọc giá trị cũ từ cache — phổ biến nhất, xảy ra trên x86
  • StoreStore reordering: 2 stores có thể đến memory theo thứ tự khác (phổ biến trên ARM, Power)
  • LoadLoad reordering: 2 loads có thể thấy kết quả khác thứ tự code (ARM, Power)

6.2 Memory Barriers (Fences)

// Ngăn reordering bằng memory barriers:
__sync_synchronize();            // GCC full memory barrier
__asm__ __volatile__("mfence"); // x86 full fence
std::atomic_thread_fence(std::memory_order_seq_cst); // C++11

// x86: chỉ cần Store/Load fence
__asm__ __volatile__("sfence"); // Store fence
__asm__ __volatile__("lfence"); // Load fence
__asm__ __volatile__("mfence"); // Full fence

7. Liên Kết Với Database: Tại Sao Điều Này Quan Trọng?

InnoDB Buffer Pool

Nhiều Buffer Pool instances để giảm contention trên L3 cache giữa các threads. Mỗi instance có mutex riêng → giảm MESI invalidation.

InnoDB Log Buffer

Ghi redo log theo block 512 bytes (= OS sector size) để tránh partial write. Alignment với hardware sector đảm bảo atomicity.
