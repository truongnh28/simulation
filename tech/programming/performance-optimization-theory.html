1. Moore's Law Đã Thay Đổi Hình Thức

Trước năm 2005, lập trình viên được miễn phí bữa ăn (free lunch): mỗi năm CPU nhanh hơn, phần mềm tự động chạy nhanh hơn mà không cần sửa code. Nay "bữa ăn miễn phí" đã kết thúc.

  • CPU không thể tăng main frequency nữa (giới hạn vật lý: tần số, nhiệt độ)
  • Thay vào đó: nhiều cores, nhiều threads, SMT
  • Phần mềm cần được viết để khai thác parallelism

2. Amdahl's Law — Giới Hạn Của Parallel Computing

Speedup(N) = 1 / ((1-P) + P/N)
-- P: tỷ lệ chương trình có thể parallelized
-- N: số processors
-- 1-P: tỷ lệ serial (không parallelized được)
-- Ví dụ: P=90%, N=10 → Speedup = 5.3x (không phải 10x!)
-- Ví dụ: P=90%, N=∞  → Speedup MAX = 10x

⚠️ Ứng Dụng Thực Tế

Trong database, lock contention là "serial section": khi tất cả threads đều phải wait cùng lock (ví dụ: InnoDB kernel mutex trong MySQL 5.5-), tăng số threads không giúp gì. Giải pháp: giảm serial section (split mutex, fine-grained locking, lock-free structures).

3. Queueing Theory — Khi Parallelism Gặp Giới Hạn

3.1 Little's Law

L = λ × W
-- L: Số request trung bình trong hệ thống
-- λ: Throughput (request/giây)
-- W: Thời gian trung bình mỗi request trong hệ thống (response time)

-- Ví dụ thực tế (iostat output):
-- r/s = 173.83, w/s = 39.22, await = 11.67ms
-- avgqu-sz = (173.83 + 39.22) × 11.67 / 1000 = 2.49 (requests in flight)

3.2 Utilization và Response Time — Quan Hệ Phi Tuyến

💡 Nguyên Tắc Capacity Planning

Giữ CPU/IO utilization dưới 70-75% để đảm bảo response time ổn định. Khi utilization vượt 80%, hệ thống bắt đầu "queuing" và response time tăng đột ngột. Đây là nguyên tắc cơ bản của capacity planning.

3.3 Kendall Notation — Mô Hình Hóa Hệ Thống

Mọi hệ thống hàng đợi có thể biểu diễn bằng ký hiệu A/S/c/K/N/D:

  • A: Phân phối thời gian đến (M=Markov, D=Deterministic, G=General)
  • S: Phân phối thời gian phục vụ
  • c: Số servers (1 đến vô hạn)
  • K: Độ dài tối đa queue
  • N: Số requests tối đa
  • D: Chiến lược scheduling (FCFS, LIFO, SIRO...)
-- M/M/1: Model đơn giản nhất, phổ biến nhất
-- Poisson arrivals (M), exponential service (M), 1 server
-- Công thức:
-- ρ = λ/μ (utilization, phải < 1)
-- W = 1/(μ-λ) (average response time)
-- Wq = ρ/(μ-λ) (average wait time)
-- L = ρ/(1-ρ) (average queue length)

💡 Jeff Dean Insight

Biết các con số này cho phép ước lượng performance mà không cần chạy code. Ví dụ: quicksort 1GB số nguyên → khoảng 30 giây (tính được từ memory bandwidth và branch misprediction rates). Viết system software mà không biết những con số này giống như thiết kế tòa nhà mà không biết vật liệu có sức chịu tải bao nhiêu.

5. MySQL Performance Evolution

5.1 MySQL 5.1/5.5 — Giai Đoạn 1: Coarse → Fine Grained

  • MySQL 5.1: Single InnoDB kernel mutex bảo vệ nhiều critical sections → severe contention
  • MySQL 5.5: Kernel mutex split thành nhiều mutex nhỏ hơn, Multiple Buffer Pool instances, Multiple purge threads

5.2 MySQL 5.6/5.7 — Giai Đoạn 2: Phần Cứng + Phần Mềm Kết Hợp

SSE Instruction Set

SIMD SSE4 cho InnoDB checksum computation. Thay thế software checksum bằng hardware CRC32 instruction → giảm CPU overhead đáng kể cho I/O.

G5 Discovery

Per-thread counter với cache line padding cho srv_n_rows_read. Kết quả: >50% scalability improvement trên Sysbench OLTP RO trong MySQL 5.6 labs release.

5.3 MySQL 8.0 — Giai Đoạn 3: Kiến Trúc Tương Lai

  • C++11, better support cho ARM64/PPC
  • Transactional data dictionary (bỏ .FRM files)
  • Cost-based optimizer với table level hints, invisible indexes
  • Atomic DDL

5.4 AliSQL — Cải Tiến Của Alibaba

Enhanced Thread Pool

Dựa trên Queueing Theory: với hàng nghìn connections, không tạo hàng nghìn threads. Thread pool giữ số threads tối ưu, tránh context switching overhead. AliSQL với Thread Pool tăng TPS từ ~5,000 lên ~50,000 khi concurrent connections cao.

Hot SKU (Hotspot Update)

Tối ưu cho e-commerce: nhiều transactions cùng update một record (VD: inventory count). 3 thế hệ cải tiến: Syntax hints → InnoDB Strict Concurrency → Row Cache + Group Update. Từ 550 TPS lên ~40,000 TPS cho hot row update!

6. Tam Đoạn Kiếm Tối Ưu Performance

Bước 1: Đo Lường Trước

Không tối ưu "mù quáng". Dùng profiler (perf, Flame Graphs, pprof) để tìm bottleneck thực sự. 80% performance ở 20% code.

Bước 2: Thuật Toán & Data Structure

Cải thiện algorithmically (O(n²) → O(n log n)) là tốt hơn bất kỳ hardware upgrade nào. Data structure cache-friendly (B-Tree vs Hash, SoA vs AoS).

Bước 3: Mechanical Sympathy

Viết code "thông cảm" với hardware: tối thiểu cache miss, tránh false sharing, dùng SIMD/vectorization, lock-free khi có thể, minimize memory allocation.

✅ Flame Graph — Công Cụ Profiling Thực Tế

perf record -g -p $(pgrep mysqld) -- sleep 30
perf script | stackcollapse-perf.pl | flamegraph.pl > mysql.svg

Nhìn vào SVG để tìm các hàm chiếm nhiều CPU nhất. Trong MySQL, phổ biến là: lock management, buffer pool scan, B-Tree traversal.
