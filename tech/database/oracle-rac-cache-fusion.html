🏛️ Oracle RAC & Cache Fusion

Real Application Cluster — kiến trúc shared-disk distributed database, Cache Fusion protocol, Split-Brain detection và Resource Distribution Algorithm

1. Oracle RAC: Khái Niệm Cốt Lõi

Oracle Real Application Clusters (RAC) là kiến trúc cho phép nhiều Oracle database instances (nodes) cùng chia sẻ một storage vật lý và hoạt động như một database thống nhất với tên gọi duy nhất. Đây là triết lý shared-disk — hoàn toàn khác với shared-nothing của MySQL Cluster hay Distributed SQL (CockroachDB, TiDB).

💡 Shared-Disk vs Shared-Nothing

Shared-Disk (RAC): Tất cả nodes đọc/ghi cùng một storage. Ưu điểm: không cần sharding data, dễ scale-up và add nodes. Nhược điểm: cần high-speed interconnect giữa nodes để đồng bộ cache, phức tạp hơn khi nodes fail đồng thời.
Shared-Nothing (MySQL Cluster, TiDB): Mỗi node sở hữu partition dữ liệu riêng. Scale tốt hơn về storage, nhưng phức tạp hơn khi cross-shard queries.

1.2 Các Thành Phần Chính

GCS — Global Cache Service

Quản lý cache coherency giữa các nodes. Biết block nào đang được hold bởi node nào, ở trạng thái nào (read/write/exclusive). Được implement bởi LMD (Lock Monitor Daemon) và LMS (Lock Manager Server) processes.

GES — Global Enqueue Service

Quản lý distributed locks (enqueues) — row locks, table locks, DDL locks. Tương đương với lock manager trong InnoDB nhưng ở cấp cluster. Dùng PCM (Parallel Cache Management) resources.

CSS — Cluster Synchronization Services

Duy trì cluster membership. Quản lý heartbeat giữa các nodes. Phát hiện node failure và trigger reconfiguration. Dùng Voting Disk để resolve split-brain.

ASM — Automatic Storage Management

Volume manager và file system của Oracle. Phân phối data files trên nhiều disks tự động (striping), mirroring, và quản lý failover khi disk fail.

2. Cache Fusion: Trái Tim Của RAC

Cache Fusion là cơ chế cho phép một node đọc block dữ liệu từ buffer cache của node khác qua interconnect, thay vì phải đọc từ disk. Đây là innovation cốt lõi biến RAC từ một cluster nhiều nodes thành một database duy nhất với "global buffer cache" ảo.

⚡ Tại Sao Cache Fusion Quan Trọng?

Không có Cache Fusion, khi Node 1 muốn sửa block X đang được Node 2 cache, Node 2 phải flush block X xuống disk, rồi Node 1 mới có thể đọc từ disk. Với Cache Fusion, Node 2 truyền block X trực tiếp cho Node 1 qua interconnect — nhanh hơn 10-100x so với disk I/O. Cache Fusion biến interconnect latency (microseconds) thành chi phí thay vì disk latency (milliseconds).

2.1 Block States Trong Cache Fusion

Mỗi block trong GCS có thể ở nhiều trạng thái khác nhau, tương tự MESI protocol của CPU cache coherence:

State Ý Nghĩa Cho Phép Số Nodes
SHARED (S) Block được cache ở nhiều nodes, chỉ đọc Read only Multiple
EXCLUSIVE (X) Chỉ một node giữ block, có quyền write Read + Write Exactly 1
NULL (N) Block không được cache hoặc đã invalidated Không có quyền gì 0
SHARED-CURRENT Block đang được read consistent nhưng chưa committed Read với CR read Multiple

2.2 Cache Fusion Flow: Read Scenario

Node 2 muốn đọc Block 42 — Gửi request đến GCS Master của Block 42 (được xác định bởi Resource Distribution Algorithm dựa trên hash)
GCS Master kiểm tra trạng thái Block 42 — Nếu Block 42 đang ở EXCLUSIVE trên Node 1, GCS gửi "downgrade" message đến Node 1
Node 1 downgrade Block 42 từ EXCLUSIVE → SHARED — Gửi block image trực tiếp đến Node 2 qua interconnect (không qua disk!)
Node 2 nhận block image — Load vào buffer cache của mình với trạng thái SHARED. Bắt đầu đọc.
GCS cập nhật directory — Record rằng Block 42 giờ ở SHARED tại cả Node 1 và Node 2
👉 [CHÈN ẢNH: Cache Fusion read flow — Node 2 request → GCS → Node 1 transfer → Node 2 receives, với thời gian ở mỗi bước]

2.3 Cache Fusion Flow: Write Scenario (Conflict)

Node 3 muốn ghi vào Block 42 — Block 42 đang ở SHARED trên Node 1 và Node 2. Node 3 gửi request EXCLUSIVE cho GCS Master.
GCS gửi "invalidate" đến Node 1 và Node 2 — Cả hai phải invalidate cached copy của Block 42 (chuyển về NULL state)
Node 1 và Node 2 ACK invalidation — Nếu block đã bị modify (dirty), phải flush dirty version lên shared storage hoặc ship current SCN đến GCS
GCS grant EXCLUSIVE cho Node 3 — Ship block image từ holder cuối cùng (node có dirty version mới nhất) đến Node 3 qua interconnect
Node 3 write vào block, tạo redo log — Block giờ ở EXCLUSIVE state chỉ trên Node 3. GCS directory update.

⚠️ Cache Fusion Overhead: "Hot Block" Problem

Khi cùng một block bị tranh chấp liên tục giữa nhiều nodes (ví dụ: sequence generator, index root block), mỗi write đều phải thực hiện cache fusion protocol — nhiều round trips qua interconnect. Đây gọi là "hot block contention" và là performance bottleneck chính trong RAC. Giải pháp: Sequence Cache (cache sequence values per-node), Hash-based partitioning để giảm cross-node conflicts.

3. Resource Distribution Algorithm

Khi cluster có N nodes, cần quyết định node nào là "master" (hay "owner") cho mỗi resource (block, lock, etc.). Oracle dùng thuật toán phân phối tĩnh dựa trên hashing.

3.1 Hash-Based Resource Ownership

-- Thuật toán xác định GCS Master cho một block:
resource_id = (file_number × 32 + block_number) MOD total_resources
node_id = resource_id MOD num_nodes

-- Với 128 hash buckets (typical):
bucket = hash(resource_id) MOD 128
master_node = bucket_to_node_mapping[bucket]

Thiết kế 128 hash buckets cho phép phân phối đều resources giữa các nodes, đồng thời có thể re-map buckets khi nodes join/leave cluster mà không cần rehash tất cả resources.

3.2 Logical vs Physical Node Mapping

RAC tách biệt Logical Node ID (0-127, các bucket) và Physical Node ID (node instance thực sự). Điều này cho phép:

Partial Failure Handling

Khi Node 2 fail, các buckets thuộc về Node 2 được re-assign đến các surviving nodes. Logical mapping thay đổi, không cần rebuild data structures.

Reconfiguration

Add node mới: một số buckets từ existing nodes được chuyển sang node mới. Gradual rebalancing, không disruptive.

👉 [CHÈN ẢNH: 128 buckets phân phối cho 4 nodes — bucket 0-31 → Node1, 32-63 → Node2, 64-95 → Node3, 96-127 → Node4, sau đó re-map khi Node3 fail]

4. Voting Disk và Split-Brain Detection

Split-brain là tình huống nguy hiểm nhất trong distributed systems: cluster bị phân tách thành hai phần, mỗi phần nghĩ mình là "toàn bộ cluster" và tiếp tục write vào shared storage. Kết quả là data corruption không thể recover.

4.1 Voting Disk: Cơ Chế Tiebreaker

🔴 Split-Brain Scenario

Network interconnect bị cắt: Node 1, 2 không thể liên lạc với Node 3, 4. Từ góc độ của Node 1-2, Node 3-4 đã "chết" và ngược lại. Nếu cả hai nhóm tiếp tục hoạt động, chúng sẽ write conflicting data vào shared storage → data corruption thảm khốc.

Voting Disk là một file đặc biệt trên shared storage (thường đặt trên 3+ disks riêng biệt). Mỗi node phải đọc/ghi được Voting Disk để có quyền tham gia cluster. Khi split-brain xảy ra:

  1. Cluster Synchronization Services (CSS) phát hiện không thể liên lạc với một số nodes
  2. Tất cả nodes đua nhau ghi "fence" vào Voting Disk
  3. Nhóm chiếm được quorum (majority) Voting Disks tồn tại
  4. Nhóm còn lại bị forced-evicted — node tự kill mình (reboot) để tránh data corruption

💡 Quy Tắc Quorum Voting Disk

Oracle khuyến nghị dùng số lẻ Voting Disks (3 hoặc 5) để luôn có majority rõ ràng. Với 3 Voting Disks: cluster yêu cầu ≥ 2 disks available. Nếu 2 trong 3 voting disks mất kết nối, cluster shutdown toàn bộ để tránh split-brain. Đây là "fail-safe" design — thà cluster down còn hơn data corruption.

4.2 Node Eviction Process

Missed Heartbeat Detection — CSS phát hiện không nhận được heartbeat từ Node X trong misscount giây (default 30s). CSS bắt đầu eviction protocol.
Voting Disk Contest — Tất cả surviving nodes race để ghi vào Voting Disk với timestamp. Winner = node ghi trước.
STONITH (Shoot The Other Node In The Head) — Bên thắng ghi vào Voting Disk một "fence message" cho Node X. Khi Node X đọc Voting Disk và thấy mình bị fence, tự reboot.
Cluster Reconfiguration — Surviving nodes trigger GCS/GES reconfiguration. Resources của Node X được phân phối lại cho surviving nodes theo Resource Distribution Algorithm.
Buffer Cache Recovery — GCS rollback các transactions chưa commit của Node X. Dirty blocks của Node X cần được recovered — nếu chưa flush lên storage, có thể đọc từ Node X's redo log (nếu accessible) hoặc từ undo tablespace.

5. PCM Resources và Global Lock Manager

PCM (Parallel Cache Management) resources là đơn vị quản lý trong GCS. Thay vì lock từng block riêng lẻ (quá nhiều), Oracle gộp nhiều blocks vào cùng một PCM resource.

5.1 Coarse-Grained vs Fine-Grained PCM

Loại PCM Mô Tả Ưu Điểm Nhược Điểm
Coarse-Grained Nhiều blocks share một PCM resource (N:1) Ít lock overhead, GCS directory nhỏ hơn False sharing — lock conflict dù không cùng block
Fine-Grained Mỗi block có PCM resource riêng (1:1) Không false sharing, conflict chính xác hơn Nhiều GCS resources, memory overhead cao

Oracle tự động chuyển từ coarse-grained sang fine-grained (PCM "re-mastering") cho các blocks bị tranh chấp nhiều. Đây là adaptive optimization — hot blocks tự nhiên được quản lý tốt hơn.

5.2 Lock Mastering và Dynamic Remastering

PCM resource master có thể được di chuyển (dynamic remastering) để đặt gần node thường access nhất. Nếu Node 2 liên tục request resource R, GCS có thể chuyển master của R từ Node 1 sang Node 2 — giảm round trip từ 2 messages xuống 1.

⚠️ RAC Không Phải Silver Bullet

RAC giải quyết high availability và node-level scale-up, nhưng không thực sự giải quyết write scale-out. Khi write hotspot xuất hiện (cùng block bị nhiều nodes tranh giành), Cache Fusion traffic tăng cao và interconnect trở thành bottleneck. Nhiều tổ chức nhầm lẫn rằng thêm nodes vào RAC sẽ tăng throughput tuyến tính — điều này không đúng trong write-heavy workloads.

7. Kết Luận: Giá Trị Và Giới Hạn

Oracle RAC đại diện cho đỉnh cao của shared-disk distributed database engineering — một kiến trúc phức tạp được tối ưu qua hàng thập kỷ. Cache Fusion protocol, dynamic remastering, và split-brain prevention qua Voting Disk là những innovations thực sự ấn tượng.

Điểm Mạnh Thực Sự

  • High Availability: Active-active, không có single point of failure ở node level
  • Transparent Failover: Application không cần biết node nào chạy query
  • Oracle Ecosystem: Integration hoàn hảo với Oracle DB features (Partitioning, Advanced Analytics, etc.)
  • Mature và proven: 20+ năm production experience ở các bank, telecom lớn

Giới Hạn Cần Nhận Thức

  • Cost cực cao: Oracle RAC license + InfiniBand interconnect + SAN storage
  • Write scalability limited: Cache Fusion overhead tăng theo số nodes
  • Complexity: DBA cần expertise cao về GCS/GES tuning, interconnect sizing
  • Vendor lock-in: Migration ra khỏi Oracle cực kỳ khó khăn

✅ Bài Học Kiến Trúc Từ RAC

Dù không dùng Oracle RAC, các kỹ sư hệ thống vẫn có thể học nhiều từ kiến trúc này: (1) Cache coherence protocol giữa nhiều nodes là vấn đề khó — MESI ở CPU và Cache Fusion ở database solve cùng một dạng vấn đề theo cách khác nhau. (2) Split-brain detection cần tiebreaker bên ngoài (Voting Disk, etcd, ZooKeeper) — không thể giải quyết bằng majority vote thuần túy nếu network partition xảy ra. (3) Resource ownership distribution bằng hashing là pattern phổ biến trong distributed systems — Consistent Hashing của DynamoDB hay slot-based của Redis Cluster đều cùng tư tưởng.
