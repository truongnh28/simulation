1. Cost Model: InnoDB Tinh Toan Nhu The Nao?

MySQL Optimizer dung Cost-Based model de chon execution plan toi uu. Chia thanh 2 phan: CPU Cost va IO Cost.

1.1 IO Cost — Clustered Index

  • Full scan: IO Cost = so trang la cua clustered index (1 cost = 1 page)
  • Range scan: IO Cost = [(ranges + rows) / total_rows] * full_scan_cost

1.2 IO Cost — Secondary Index

⚠️ Secondary Index Non-Covering: Cuc Ky Dat!

Secondary index non-covering scan co IO cost = ranges + rows vi moi row phai quay lai clustered index (random I/O). Neu rows lon, day co the con dat hon full table scan. MySQL Optimizer nen (va thuong) chon full scan trong truong hop nay — do la optimization dung!

2. Range Query Optimization

Quy trinh optimizer chon index cho range query:

  1. possible_keys: Tim tat ca indexes co the dung (moi field trong WHERE co the la starting key)
  2. records_in_range: Voi moi possible_key, uoc luong so records trong range bang cach lam 2 search_path (tu root den la) de tinh records giua range start va range end
  3. Chon index co cost nho nhat

💡 Van De: records_in_range Khong On Dinh

records_in_range dua tren thong ke (statistics), co the thay doi khi du lieu thay doi. Ket qua: cung mot query co the chon execution plan khac nhau qua cac lan chay. MySQL 5.6.2+ co Persistent Statistics giu thong ke on dinh hon.

3. Join Query Optimization

  • MySQL dung nested-loop join (BNL/BKA)
  • Optimizer thu tat ca hoan vi thu tu join va chon thu tu co cost nho nhat
  • optimizer_search_depth: Do sau tim kiem (default 62 = global optimal nhung cham voi nhieu bang)

⚠️ Join Qua Nhieu Bang

So hoan vi join order = n! (n bang). Voi n=10, do 10! = 3,628,800 ket hop. Nen giam optimizer_search_depth hoac dung STRAIGHT_JOIN khi biet thu tu join tot. OLTP nen co index tot va tranh join qua nhieu bang trong 1 query.

4. Index Condition Pushdown (ICP)

ICP (MySQL 5.6+) cho phep Storage Engine tu filter records tren index truoc khi return len MySQL Server layer:

-- Khong co ICP:
-- 1. SE scan index, return tat ca records trong range
-- 2. MySQL Server filter theo WHERE condition
-- 3. Apply Table Filter tren clustered index

-- Co ICP:
-- 1. SE scan index
-- 2. SE filter Index Filter tren index NGAY TAI Storage Engine
-- 3. Chi return records pass Index Filter
-- 4. MySQL Server apply Table Filter

✓ ICP va Lock

ICP khong chi giam I/O ma con giam so luong locks: trong RR isolation, chi lock records pass Index Filter, khong lock records bi filter out. Loi ich kep: hieu nang + giam lock contention.

5. Case Study: Wrong Execution Plan

-- Bang: TB_IMGOUT_Picture(ID PK, UserId, DeleteState, ...)
-- Index: IDX_UID_ID(UserId, ID)
-- Query:
SELECT * FROM TB_IMGOUT_Picture 
WHERE (2601629 > ID) AND (UserId = 129329421) AND (DeleteState = 0) 
ORDER BY ID DESC LIMIT 100;

-- Optimizer chon sai: IDX_UID_ID voi 149830 rows estimated
-- Dung tay: force index
SELECT * FROM TB_IMGOUT_Picture FORCE INDEX (IDX_UID_ID) 
WHERE ...;

Nguyen nhan: records_in_range uoc luong sai do thong ke cu. Giai phap: ANALYZE TABLE hoac Persistent Statistics (5.6.2+).

6. SQL Where Condition Phan Tich

De hieu query dung index nhu the nao, phan tich WHERE thanh 3 phan:

Index Key

Dieu kien xac dinh scan range tren index. Dung de xac dinh dau/cuoi cua B-Tree scan.

pubtime > 1 AND pubtime < 20

Index Filter

Dieu kien co the check tren index nhung khong la range boundary. Dung boi ICP trong Storage Engine.

userid = 'hdc'

Table Filter

Chi check duoc tren clustered index (full record). Khong the pushdown xuong Storage Engine.

comment IS NOT NULL

7. Best Practices Toi Uu Query

  • Dung EXPLAIN de hieu execution plan truoc khi optimize
  • Uu tien covering index de tranh clustered index lookup (Index Only Scan)
  • Giam possible_keys bang cach dat index chinh xac (tranh over-indexing)
  • Tranh function tren index column trong WHERE (vi du: WHERE YEAR(created_at) = 2024)
  • Dung FORCE INDEX hoac optimizer hints khi biet execution plan tot hon optimizer
  • Enable Persistent Statistics (MySQL 5.6+) va chay ANALYZE TABLE dinh ky
