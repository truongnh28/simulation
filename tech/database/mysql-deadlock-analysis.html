💀 Nghệ Thuật Phân Tích Deadlock MySQL InnoDB

Từ nguyên lý đến thực tiễn: 4 nguyên tắc vàng phân tích deadlock và case studies sản xuất thực tế

1. Tại Sao Deadlock Khó Phân Tích?

Deadlock trong MySQL InnoDB khó debug vì: (1) logic khóa phức tạp, khó hiểu hết các loại lock và khi nào chúng được đặt; (2) MySQL mặc định chỉ ghi rất ít thông tin trong deadlock log; (3) deadlock thường xảy ra giao thoa với trạng thái runtime khó tái hiện.

💡 Phương Pháp Phân Tích Cốt Lõi

Việc phân tích deadlock bắt buộc phải: (1) hiểu đầy đủ SQL query và transaction logic, (2) biết các loại lock InnoDB có thể đặt, (3) vẽ sơ đồ lock order cho mỗi transaction, (4) tìm chu kỳ trong đồ thị wait-for.

2. Case Study 1: Deadlock Cơ Bản Nhất

-- Cấu trúc bảng:
CREATE TABLE T1 (id INT PRIMARY KEY, name VARCHAR(50));
-- Dữ liệu: (1,aaa), (2,ccc), (3,aaa), (4,bbb), (5,ccc), (6,zzz)

-- Session 1:
BEGIN;
SELECT * FROM t1 WHERE id = 1 FOR UPDATE;   -- (1) Giữ X(id=1)
UPDATE t1 SET name='qqq' WHERE id = 5;       -- (3) Muốn X(id=5) → wait!

-- Session 2 (đồng thời):
BEGIN;
DELETE FROM t1 WHERE id = 5;                 -- (2) Giữ X(id=5)
DELETE FROM t1 WHERE id = 1;                 -- (4) Muốn X(id=1) → DEADLOCK!

✅ Nguyên Tắc 1: Hiểu Toàn Bộ Transaction Logic

Phải nhìn toàn bộ transaction, không chỉ từng SQL đơn lẻ. Deadlock xảy ra khi HAI transaction giữ lock của nhau và chờ lock của nhau. Trong ví dụ trên: S1 giữ X(1) chờ X(5), S2 giữ X(5) chờ X(1) → chu kỳ.

3. Case Study 2: Deadlock Với Nhiều Index

CREATE TABLE tu (id INT PRIMARY KEY, u INT UNIQUE KEY, a INT KEY);

-- Session 1:
UPDATE tu SET u=4 WHERE a=3;
-- Thứ tự lock: X(a-index, a=3) → X(primary, id=3)

-- Session 2 (đồng thời):
UPDATE tu SET a=4 WHERE u=3;
-- Thứ tự lock: X(u-index, u=3) → X(primary, id=3)
-- Hai sessions giữ lock đầu tiên và chờ lock thứ hai → DEADLOCK!

⚠️ Nguyên Tắc 3: Nhiều Index, Cùng Record = Rủi Ro Cao

Khi hai transactions update cùng một record qua các index khác nhau, thứ tự lấy lock trên clustered index có thể ngược nhau → deadlock. Giải pháp: đảm bảo mọi update đến record X luôn đi qua cùng một index (hoặc thêm index hint).

4. Case Study 3: Gap Lock và INSERT Deadlock

CREATE TABLE t (c1 INT PRIMARY KEY AUTO_INCREMENT, c2 INT UNIQUE KEY);
-- Dữ liệu: (1,1), (5,4), (20,20)

-- T2: INSERT INTO t VALUES (null, 10);  -- giữ X(c2=10) + X(primary)
-- T1: INSERT INTO t VALUES (null, 10);  -- wait: cần S-lock để check unique
-- T2: INSERT INTO t VALUES (null, 9);   -- cần Gap Lock (4,10) → bị block!
-- → DEADLOCK!

Khi INSERT vào giá trị đã tồn tại trong Unique Index, InnoDB cần thêm S-lock với Next-Key semantic để check uniqueness. Điều này có thể gây deadlock phức tạp trong môi trường concurrent.

🚨 Nguyên Tắc 4: Gap Lock + Unique Index = Deadlock Bất Ngờ

Concurrent inserts vào cùng một unique key value là nguồn gây deadlock khó hiểu nhất trong production MySQL. Luôn add retry logic cho error 1213 (deadlock) ở application layer.

5. Đọc và Hiểu Deadlock Log

SHOW ENGINE INNODB STATUS;
-- Các chuỗi lock mode quan trọng:
-- "lock_mode X locks rec but not gap"  → Record X Lock
-- "lock_mode X"                         → Next-Key Lock (Record + Gap)
-- "lock_mode X locks gap before rec"    → Gap Lock only
-- "lock_mode X locks gap before rec insert intention" → Insert Intention Lock

6. 4 Nguyên Tắc Vàng Phòng Tránh Deadlock

⭐ Nguyên Tắc 1: Hiểu Business Logic

Phân tích deadlock bắt buộc phải hiểu toàn bộ business transaction. Không thể chỉ nhìn log mà cần biết transaction làm gì.

⭐ Nguyên Tắc 2: Dùng RC Isolation

Gap Lock phức tạp và gây nhiều deadlock. Dùng RC isolation + row-based binlog để loại bỏ Gap Lock, giảm deadlock đáng kể.

⭐ Nguyên Tắc 3: Tránh Nhiều Index Trên Cùng Record

Khi update record X qua index A, rủi ro deadlock với transaction update X qua index B. Thống nhất index access path nếu có thể.

⭐ Nguyên Tắc 4: Thứ Tự Nhất Quán

Đảm bảo các transactions lấy lock theo cùng thứ tự trên các resources. Deadlock chỉ xảy ra khi có 2+ transactions lấy lock theo thứ tự đảo ngược.

7. Checklist Khi Gặp Deadlock Production

  1. Bật innodb_print_all_deadlocks=ON
  2. Lấy deadlock log từ SHOW ENGINE INNODB STATUS hoặc error log
  3. Xác định các transactions tham gia và SQL của chúng
  4. Xác định lock order của từng transaction
  5. Tìm chu kỳ trong wait-for graph
  6. Tìm nguồn gốc: Gap Lock? Unique constraint? Multi-index access?
  7. Đề xuất fix: đổi isolation level, đổi index, đổi lock order, retry logic

✅ Always Add Retry Logic

Deadlock là chuyện bình thường trong concurrent systems — quan trọng là handle nó gracefully. Application luôn cần có retry logic cho error 1213.
