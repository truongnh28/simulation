1. AliSQL Là Gì Và Tại Sao Cần Nó?

AliSQL là nhánh MySQL (MySQL fork) do Alibaba phát triển từ năm 2010, được dẫn dắt bởi nhóm kernel database do kỹ sư He Dengcheng (何登成) đứng đầu. Đây không phải một dự án research thuần túy — nó được sinh ra từ áp lực vận hành thực tế của hệ thống thương mại điện tử lớn nhất thế giới.

Alibaba không thể chờ đợi upstream MySQL release mới để giải quyết các vấn đề hiệu năng cấp bách. Một sự kiện Double 11 (11.11 — Singles' Day) có thể tạo ra hàng triệu giao dịch mỗi giây trong khung thời gian đỉnh. MySQL "vanilla" không được thiết kế cho kịch bản này — vì vậy Alibaba phải tự xây dựng giải pháp và đó chính là AliSQL.

Hiệu Năng (Performance)

MySQL gốc có nhiều bottleneck khi scale lên hàng chục cores và hàng nghìn connections. AliSQL loại bỏ từng bottleneck một qua thực tiễn production.

Tính Năng (Features)

Các use case của Alibaba đòi hỏi tính năng không có trong MySQL — Hot SKU update, K-V interface, commit hints, flow control...

Vận Hành (Operations)

DBA cần visibility tốt hơn (deadlock info, lock timeout per-SQL), tự động phát hiện và sửa inconsistency, kiểm soát lưu lượng linh hoạt.

3. Hot SKU — Bài Toán Kinh Điển Và Hành Trình Giải Quyết

Hot SKU (Stock Keeping Unit) là vấn đề điển hình nhất của e-commerce: hàng chục nghìn người dùng đồng thời mua cùng một sản phẩm hot, tất cả đều cần UPDATE cùng một row trong database để giảm số lượng tồn kho. Đây là row lock contention ở dạng cực đoan nhất.

🚨 Vấn Đề: Row Lock Contention Cực Đoan

Với MySQL vanilla, khi 1,000 users đồng thời chạy UPDATE inventory SET qty = qty - 1 WHERE sku_id = 12345: chỉ 1 transaction có thể giữ row lock tại một thời điểm. 999 transactions còn lại phải chờ. Thời gian chờ tăng tuyến tính → throughput giảm mạnh → nhiều deadlock → transaction timeout. Điểm bottleneck: một row database trở thành "điểm nút cổ chai" của toàn hệ thống.

Thế Hệ 1: Syntax Hints

Thêm hints vào SQL để InnoDB biết đây là hot row update, xử lý ưu tiên. Cải thiện nhỏ nhưng không giải quyết được gốc rễ — vẫn phải serialize qua lock.

~550 TPS → ~2,000 TPS

Thế Hệ 2: InnoDB Strict Concurrency

Giới hạn số threads đồng thời vào InnoDB kernel để giảm lock contention. Queue ở tầng trên, serialize trước khi vào storage engine.

~2,000 TPS → ~10,000 TPS

Thế Hệ 3: Group Update

Gom nhiều UPDATE cùng một row thành một group update nguyên tử. 1 lock → 1 lần UPDATE thực thi thay cho N lần. Hỗ trợ rollback, không lost update.

~40,000–100,000 TPS 🚀

3.1 Cơ Chế Group Update — Phân Tích Sâu

Group Update là một trong những đổi mới thú vị nhất của AliSQL vì nó thay đổi ngữ nghĩa của transaction theo cách tinh tế:

-- Thay vì N transactions riêng lẻ:
-- T1: UPDATE inventory SET qty = qty - 1 WHERE id = 100; COMMIT;
-- T2: UPDATE inventory SET qty = qty - 1 WHERE id = 100; COMMIT;
-- ...Tn: UPDATE inventory SET qty = qty - 1 WHERE id = 100; COMMIT;

-- AliSQL Group Update gom thành:
-- Detect: nhiều pending updates trên cùng row id=100
-- Execute: UPDATE inventory SET qty = qty - N WHERE id = 100; COMMIT;
-- Notify: N transactions được notify thành công/thất bại

-- Binlog ghi 1 operation thay vì N → Slave cũng nhanh hơn!

💡 Tại Sao Group Update Không Đơn Giản

Thách thức kỹ thuật: nếu một trong N transactions trong group cần rollback (do ràng buộc khác), làm thế nào để rollback đúng? AliSQL giải quyết bằng cách ghi riêng delta của từng transaction trong undo log, nhưng chỉ thực thi một lần ở tầng storage. Nếu group update thành công mà transaction riêng lẻ cần rollback, chỉ rollback delta của transaction đó — không ảnh hưởng các transaction khác trong group.

4. Thread Pool — Queueing Theory Trong Thực Tiễn

Enhanced Thread Pool của AliSQL là ứng dụng trực tiếp của Queueing Theory (Erlang-C formula) vào database architecture. Thay vì tạo 1 thread cho mỗi connection (mô hình truyền thống của MySQL), Thread Pool duy trì một số lượng thread tối ưu phục vụ N connections (N >> số thread).

MySQL Truyền Thống — 1 Thread/Connection

10,000 connections → 10,000 threads

  • Context switch overhead: >95% CPU time
  • Memory: ~8MB/thread × 10K = 80GB
  • Cache thrashing: TLB và L1/L2 bị invalidate liên tục
  • Lock contention tăng cấp số nhân
~5,000 TPS

Degradation khi concurrent connections tăng cao

AliSQL Thread Pool — Tối Ưu Theo Erlang-C

10,000 connections → ~128 worker threads

  • Context switch tối thiểu (số thread ≈ số core)
  • Memory: 128 × 8MB = 1GB
  • Cache warm: mỗi thread xử lý liên tục cùng loại query
  • Lock granularity cao hơn, ít contention
~50,000 TPS

Tăng 10× khi concurrent connections cao 🚀

5.2 X-KV Protocol — Thiết Kế Mới

InnoDB Memcached Plugin dùng delimiter để phân tách các cột — ví dụ dùng ký tự |. Vấn đề: nếu data chứa ký tự | thì sao? Không có NULL-safe cách nào. X-KV thiết kế protocol mới dựa trên length-encoding:

-- InnoDB Memcached cũ (delimiter-based):
PK=1 | NAME=He Dengcheng | WORKPLACE=阿里巴巴西溪园区 |
-- Vấn đề: nếu value chứa | thì protocol bị vỡ

-- X-KV Protocol mới (length-based):
Field = Meta Info + Data

Meta Info: [Version][Count][Length1][Length2][Length3]...
Data:      [value1][value2][value3]...

-- Ví dụ:
[0][3][1][14][10] [1] [He Dengcheng] [阿里巴巴西溪]
 ^  ^  ^   ^   ^   ^        ^               ^
Ver Cnt L1  L2  L3  C1       C2              C3

-- Hỗ trợ composite index:
GET [table_name.]key1 [key2] [key3]

6. commit_on_success — Tối Ưu Replication Không Mất Dữ Liệu

Một trong những bottleneck ẩn nhất trong MySQL replication: sau mỗi transaction commit, client phải nhận ACK từ master, rồi master mới ghi binlog để slave replicate. commit_on_success hint của AliSQL loại bỏ một roundtrip network.

-- Query thông thường (2 roundtrips):
-- Client → Master: BEGIN; UPDATE ...; COMMIT;  [roundtrip 1]
-- Master → Client: OK                           [roundtrip 2: ACK]
-- Master → Slave: binlog event                  [async]

-- commit_on_success hint (1 roundtrip):
INSERT INTO orders VALUES (...) COMMIT_ON_SUCCESS ROLLBACK_ON_FAIL;
-- Client gửi query kèm hint
-- Master thực thi + commit + reply trong 1 response
-- Nếu fail: tự động rollback, thông báo lỗi cho client
-- Giảm 50% network roundtrip cho write-heavy workloads!

💡 Ý Nghĩa Đối Với Replication

commit_on_success kết hợp với Enhanced Semi-Sync Replication của AliSQL đảm bảo: transaction chỉ được commit ở master sau khi ít nhất 1 slave đã nhận và ghi binlog. Điều này loại bỏ hoàn toàn tình huống "master commit, slave chưa nhận, master crash" — nguyên nhân của data loss trong setup master-slave truyền thống. AliSQL đạt được strong consistency với minimum overhead.

7. X-Cluster — Giải Pháp Cluster Trên X-Paxos

X-Cluster là bước tiến xa nhất của AliSQL: không chỉ tối ưu một instance, mà xây dựng distributed consensus cluster. X-Cluster dựa trên X-Paxos — implementation Multi-Paxos của Alibaba được tối ưu cho database workloads.

Tại Sao Không Dùng MySQL Group Replication?

  • MySQL Group Replication dùng Paxos nhưng implementation chưa đủ mature cho Alibaba scale
  • X-Paxos được tối ưu đặc biệt cho low-latency: pipeline nhiều round Paxos, batch commit
  • Tích hợp sâu với AliSQL engine — không phải plugin ngoài
  • Battle-tested qua nhiều Double 11 trước khi công bố

Đảm Bảo Của X-Cluster

  • Strong Consistency: Mỗi write được đa số nodes xác nhận trước khi visible
  • Automatic Failover: Leader election tự động trong milliseconds khi master fail
  • No Data Loss: Không bao giờ mất transaction đã commit
  • Linear Scalability: Read có thể scale bằng cách thêm Follower nodes

8. Select from Update — Đọc Giá Trị Trước Khi Ghi

Một tính năng tinh tế nhưng rất hữu ích trong e-commerce: thường cần SELECT xem giá trị hiện tại trước khi UPDATE (để kiểm tra logic). Với MySQL vanilla, cần 2 statements. AliSQL thêm cú pháp:

-- MySQL thông thường: 2 roundtrips
SELECT price FROM products WHERE id = 100;  -- kiểm tra giá
UPDATE products SET price = 99 WHERE id = 100 AND price = 100;  -- conditional update

-- AliSQL SELECT_FROM_UPDATE: 1 roundtrip
UPDATE products SET price = 99
WHERE id = 100 AND price = 100
RETURNING price_before, price_after;

-- Hoặc:
SELECT * FROM (UPDATE inventory SET qty=qty-1 WHERE sku_id=12345) AS old_state;
-- Trả về giá trị CŨ của row trước khi update — rất hữu ích cho audit log!

Điều AliSQL Dạy Về Database Engineering

  • Bottleneck không phải lúc nào cũng ở nơi bạn nghĩ: srv_n_rows_read++ — một dòng code đơn giản gây false sharing, fix nó tăng 50% scalability
  • Theory drives practice: Thread Pool từ Erlang-C, không phải trial-and-error
  • Measure first: Mọi optimization đều bắt đầu từ profiling thực tế, không từ assumption

Các Công Ty Học Từ AliSQL

  • PolarDB: Thế hệ tiếp theo của Alibaba, xây trên AliSQL experience
  • TiDB: Học từ Hot SKU solution khi thiết kế row-level conflict detection
  • OceanBase: X-Paxos experience ảnh hưởng đến Paxos implementation
  • MySQL 8.0: Nhiều optimizations tương tự AliSQL xuất hiện trong MySQL 8.0

🔗 Liên Kết Đa Lĩnh Vực

AliSQL là điểm hội tụ của tất cả các lý thuyết trong bộ tài liệu này:

  • Queueing Theory → Thread Pool (Erlang-C optimal threads), Hot SKU queue/batch
  • CPU Cache Coherence → G5 Discovery (false sharing fix trong srv_n_rows_read), per-thread counters
  • Amdahl's Law → Split kernel mutex (InnoDB 5.5), multiple buffer pool instances → giảm serial section
  • Paxos/Raft → X-Cluster dựa trên X-Paxos, Enhanced Semi-Sync tương tự 2PC nhẹ
  • Memory Model → Dual redo log buffers cần memory barriers chính xác để thread-safe

AliSQL không phải collection của các tính năng ngẫu nhiên — đó là ứng dụng có hệ thống của lý thuyết máy tính hiện đại vào một bài toán thực tế cực đoan.
