🔬 MySQL 5.6 InnoDB: Cải Tiến Sâu

Read-Only Transaction optimization, Buffer Pool Flushing algorithm mới, Page Cleaner thread, Multi-Purge, và CRC32 qua SSE4.2 — phân tích kỹ thuật từ bên trong InnoDB

1. Bối Cảnh: Tại Sao MySQL 5.6 Là Bước Ngoặt?

MySQL 5.6 (released 2013) đánh dấu giai đoạn InnoDB chuyển đổi từ "single-server monolith" sang "multi-core optimized engine". Các phiên bản trước (5.1, 5.5) có nhiều global mutexes và shared data structures khiến performance không scale theo số CPU cores. MySQL 5.6 attack các bottleneck này một cách có hệ thống.

~3x
Read-only TPS tăng (trên 48 cores)
4
Page Cleaner threads (từ 1)
32x
Nhanh hơn CRC32 với SSE4.2

2. Read-Only Transaction Optimization

Trong MySQL 5.5, mọi transaction — dù chỉ đọc — đều phải cấp phát Transaction ID và được thêm vào global transaction list. Điều này gây contention nặng trên các shared structures khi có nhiều concurrent readers.

2.1 Vấn Đề Trong MySQL 5.5

// MySQL 5.5: Mọi transaction đều:
1. Lấy trx_sys->mutex (global mutex!)
2. Cấp phát transaction ID từ trx_sys->max_trx_id
3. Thêm vào trx_sys->trx_list (global read-write list)
4. Tạo Read View
5. Khi commit: xóa khỏi trx_list, release mutex

// Với 100 concurrent readers, 100 threads tranh nhau 1 mutex
// → Linear scalability không đạt được trên multi-core

2.2 Giải Pháp Trong MySQL 5.6

MySQL 5.6 phân loại transactions thành Read-Only (RO) và Read-Write (RW):

💡 Phân Loại Read-Only Transaction

Transaction được auto-detected là RO nếu: (1) không có bất kỳ INSERT/UPDATE/DELETE nào, hoặc (2) explicit START TRANSACTION READ ONLY. Nếu sau đó có write, InnoDB dynamically upgrade lên RW transaction.

RO Transaction: Không Cần Transaction ID

RO transactions không cần global Transaction ID vì chúng không tạo undo log và không visible trong MVCC history. Chỉ cần snapshot timestamp (Global SCN) để tạo Read View.

Separate RO Transaction List

RO transactions được thêm vào ro_trx_list riêng biệt. RW transactions dùng rw_trx_list. Purge chỉ cần scan rw_trx_list — giảm contention đáng kể.

2.3 CACHE_LINE_SIZE Padding: Tránh False Sharing

Một tối ưu tinh tế khác là padding các counters để mỗi counter nằm trên cache line riêng (64 bytes):

// MySQL 5.5 — counters liền kề nhau → false sharing
struct trx_sys_t {
    ulint  n_ro_trx;   // offset 0
    ulint  n_rw_trx;   // offset 8 → cùng cache line với n_ro_trx!
    ...
};

// MySQL 5.6 — pad ra để mỗi counter trên cache line riêng
struct trx_sys_t {
    ulint  n_ro_trx;
    char   pad1[CACHE_LINE_SIZE - sizeof(ulint)];  // fill to 64 bytes
    ulint  n_rw_trx;
    char   pad2[CACHE_LINE_SIZE - sizeof(ulint)];
    ...
};

⚡ Tại Sao False Sharing Nguy Hiểm?

Cache line là đơn vị transfer nhỏ nhất giữa CPU và cache (64 bytes). Nếu n_ro_trx (được update bởi Thread A) và n_rw_trx (được update bởi Thread B) nằm trên cùng cache line, mỗi khi Thread A update n_ro_trx, cache line đó bị invalidated trên CPU của Thread B — dù Thread B không quan tâm đến n_ro_trx. Padding giải quyết triệt để bằng cách đảm bảo chúng ở cache lines khác nhau. Kỹ thuật này còn gọi là "cache line isolation" hay "padding to cache line boundary".

3. Buffer Pool Flushing: Thuật Toán Mới

InnoDB Buffer Pool chứa dirty pages (pages đã sửa nhưng chưa ghi xuống disk). Flushing dirty pages phải cân bằng: flush quá ít → disk checkpoint lag sau WAL, flush quá nhiều → I/O spike gây latency tăng đột ngột.

3.1 Vấn Đề Với Adaptive Flushing Cũ

MySQL 5.5 dùng Adaptive Flushing nhưng algorithm đơn giản: chỉ dựa trên số dirty pages hiện tại. Khi dirty page ratio vượt ngưỡng, flush tăng đột ngột. Kết quả là I/O pattern "burst" — yên tĩnh rồi đột ngột flush nhiều — gây latency spike không mong muốn.

3.2 avg_page_rate Algorithm Trong MySQL 5.6

MySQL 5.6 giới thiệu thuật toán mới dựa trên rate of dirty page generation thay vì absolute count:

// Tính rate dirty pages mới được tạo trong Δt giây
avg_page_rate = (dirty_pages_current - dirty_pages_prev) / delta_t;

// Tính LSN advancement rate (WAL generation rate)
lsn_rate = (current_lsn - prev_lsn) / delta_t;

// Target flush rate để checkpoint lag không quá lớn
target_flush_rate = max(
    avg_page_rate,           // ít nhất bằng tốc độ dirty tạo mới
    lsn_rate / max_modified_age  // đảm bảo checkpoint không lag quá xa
);

// Nếu target > actual flush rate → tăng tốc flush
// Nếu target < actual flush rate → giảm tốc flush (giảm I/O pressure)

✅ Kết Quả: Smooth I/O Pattern

Thay vì flush "bursty", algorithm mới tạo ra flush pattern đều đặn, ổn định. Latency percentile (p99, p999) giảm đáng kể vì không có I/O spike đột ngột. Đây là tư duy "control theory" áp dụng vào database engineering — điều chỉnh rate liên tục để maintain steady state.

3.3 Checkpoint Age và Redo Log Pressure

InnoDB có redo log với kích thước cố định (vòng lặp). Checkpoint LSN phải tiến đủ nhanh để tránh overwrite redo log chưa được flushed. MySQL 5.6 thêm metric checkpoint_age_async và checkpoint_age_sync:

Checkpoint State Điều Kiện Hành Động Ảnh Hưởng
Normal checkpoint_age < async_water_mark Flush theo target rate bình thường Không có impact
Async Flush async_water_mark ≤ age < sync_water_mark Tăng flush rate thêm I/O tăng nhẹ
Sync Flush age ≥ sync_water_mark Block user transactions, force flush Latency spike nghiêm trọng

⚠️ Ngăn Ngừa Sync Flush

Sync Flush (blocking user transactions) là tình huống tệ nhất cần tránh. Để ngăn: (1) innodb_io_capacity đủ cao để flush bắt kịp write rate; (2) innodb_log_file_size đủ lớn để có room cho redo log; (3) Monitor Innodb_checkpoint_age và alert khi >80% của innodb_log_file_size.

4. Page Cleaner Thread: Từ 1 Lên 4

Trong MySQL 5.5, chỉ có một Page Cleaner thread duy nhất chịu trách nhiệm flush tất cả dirty pages từ tất cả buffer pool instances. Đây là bottleneck rõ ràng khi innodb_buffer_pool_instances > 1.

4.1 Multi-Threaded Page Cleaner

MySQL 5.6 giới thiệu innodb_page_cleaners (default: 4, max: 64). Mỗi Page Cleaner thread phụ trách một số buffer pool instances nhất định:

-- MySQL 5.5: 1 page cleaner → tất cả buffer pool instances
-- MySQL 5.6:
innodb_page_cleaners = 4
innodb_buffer_pool_instances = 8

-- Thread 0: BP instance 0, 1
-- Thread 1: BP instance 2, 3
-- Thread 2: BP instance 4, 5
-- Thread 3: BP instance 6, 7

💡 Tại Sao innodb_page_cleaners ≤ innodb_buffer_pool_instances?

Mỗi Page Cleaner cần ít nhất một buffer pool instance để work on. Setting page_cleaners > buffer_pool_instances vô nghĩa — các extra threads sẽ idle. Best practice: set chúng bằng nhau, hoặc page_cleaners = buffer_pool_instances / 2 nếu I/O bandwidth không đủ.

4.2 Coordinator Thread

Một trong N Page Cleaner threads đóng vai trò "Coordinator": tính toán flush targets, distribute work cho các worker threads, và handle synchronization với Checkpoint mechanism.

5. Multi-Purge Threads

Purge là quá trình dọn dẹp undo log records không còn cần thiết (không có active transaction nào cần đọc version cũ nữa). MySQL 5.5 dùng 1 purge thread — bottle neck khi write throughput cao.

5.1 Vấn Đề Với Single Purge Thread

Single purge thread phải xử lý tuần tự: scan history list → identify purgeable records → remove from undo logs → remove secondary index entries (đây là bước chậm nhất). Khi write throughput cao, purge lag sau và undo log space tăng không ngừng → disk space leak, và MVCC visibility check chậm hơn.

5.2 Multi-Purge trong MySQL 5.6

-- Cấu hình:
innodb_purge_threads = 4  -- default 4, max 32

-- Architecture:
-- 1 Coordinator Thread: scan history list, identify work
-- N-1 Worker Threads: thực hiện purge records song song

-- Coordinator phân công theo table/tablespace để tránh conflict

Coordinator Thread

Scan trx_sys→history_list theo thứ tự commit. Xác định records nào có thể purge (không còn trong snapshot của bất kỳ active transaction nào). Tạo "purge tasks" và distribute cho workers.

Worker Threads

Nhận tasks từ coordinator qua work queue. Thực hiện purge undo log records và update secondary indexes. Parallel execution → tăng throughput 3-4x so với single thread.

⚡ Tương Quan Với InnoDB MVCC

Purge thread chỉ xóa records khi chúng "below low water mark" — tức là không có active Read View nào cần đọc version đó. low_limit_id trong Read View xác định ngưỡng này. Nếu có long-running transactions (nhiều giờ), purge bị block và undo log space bloat. Đây là lý do luôn commit/rollback transactions sớm nhất có thể trong production.

6. CRC32 Qua SSE4.2: Hardware Acceleration

InnoDB dùng checksum để phát hiện data corruption (bit flips, partial writes). Checksum được tính cho mỗi page (16KB) khi write và verify khi read. Với Buffer Pool lớn và nhiều I/O, checksum computation có thể là CPU bottleneck.

6.1 Từ CRC32 Software Đến Hardware Instruction

Method Throughput CPU Cycles / byte Ghi Chú
InnoDB legacy checksum ~0.5 GB/s ~8 Pure software, complex algorithm
CRC32 software (table lookup) ~1 GB/s ~4 Lookup table, better than legacy
CRC32 SSE4.2 hardware ~16 GB/s ~0.25 32x nhanh hơn legacy

6.2 SSE4.2 CRC32 Instruction

// Intel SSE4.2 cung cấp instruction CRC32:
// _mm_crc32_u64(crc, data) — tính CRC32 cho 8 bytes trong 1 clock cycle

// InnoDB implementation:
uint32_t crc32_hardware(const unsigned char *buf, uint32_t len) {
    uint32_t crc = 0xFFFFFFFF;

    // Process 8 bytes at a time using SSE4.2
    while (len >= 8) {
        crc = _mm_crc32_u64(crc, *(uint64_t*)buf);
        buf += 8;
        len -= 8;
    }
    // Handle remaining bytes
    while (len--) {
        crc = _mm_crc32_u8(crc, *buf++);
    }
    return ~crc;
}

// Kiểm tra CPU support tại startup:
if (cpuid_flags & CPUID_SSE42) {
    innodb_checksum_algorithm = CRC32;
} else {
    innodb_checksum_algorithm = INNODB;  // fallback
}

💡 Liên Kết Với CPU Architecture

SSE4.2 CRC32 instruction là ví dụ hoàn hảo của hardware-software co-design: CPU manufacturers nhận thấy CRC32 là common operation trong storage và networking, nên built-in dedicated circuit. InnoDB exploit điều này để giảm CPU overhead từ 8 cycles/byte xuống 0.25 cycles/byte — improvement 32x chỉ bằng cách dùng đúng instruction. Tương tự: AES-NI cho encryption, AVX-512 cho ML inference, SHA-NI cho hash computation.

6.3 Checksum Algorithm Migration

MySQL 5.6 hỗ trợ 3 checksum algorithms: INNODB (legacy), CRC32 (mới, hardware-accelerated), NONE (không dùng). Vấn đề: tablespace files cũ dùng INNODB checksum, files mới dùng CRC32 → không thể đọc lẫn nhau nếu set sai.

-- Kiểm tra algorithm đang dùng:
SHOW VARIABLES LIKE 'innodb_checksum_algorithm';

-- Migration sang CRC32:
SET GLOBAL innodb_checksum_algorithm = 'strict_crc32';
-- Sau đó restart và rebuild tablespaces (ALTER TABLE ... FORCE)

✅ Bài Học Kiến Trúc Từ MySQL 5.6

MySQL 5.6 là case study xuất sắc về systematic scalability engineering. Không phải một single big rewrite, mà là nhiều targeted optimizations: (1) Giảm global mutex scope bằng fine-grained structures; (2) Eliminate false sharing qua cache line alignment; (3) Chuyển từ threshold-based sang rate-based control; (4) Parallelize serial bottlenecks (cleaner, purge); (5) Exploit hardware instructions. Mỗi cải tiến độc lập nhưng cùng hướng về một mục tiêu: multi-core scalability. Đây là cách tiếp cận đúng đắn khi performance engineering một system phức tạp.
