🔒 InnoDB Transaction, Lock & MVCC

Phân tích toàn diện cơ chế giao dịch, hệ thống khóa và kiểm soát đồng thời đa phiên bản trong MySQL InnoDB

1. Tổng Quan Kiến Trúc InnoDB

InnoDB là storage engine mặc định của MySQL, được thiết kế theo kiến trúc module hóa cao. Toàn bộ engine chia thành nhiều tầng: OS layer (tương tác với hệ điều hành), Lock (quản lý khóa), Transaction (quản lý giao dịch), Multiversion (MVCC), Log/Recovery (redo/undo), Index (B+Tree), Buffer Pool và Handler layer.

💡 Tại sao kiến trúc module hóa quan trọng?

Việc tách biệt các module giúp mỗi thành phần có thể được tối ưu độc lập. Ví dụ: Alibaba đã tối ưu riêng module Lock để cải thiện throughput trong AliSQL mà không ảnh hưởng đến logic Transaction.

2. Giao Dịch InnoDB (Transaction)

2.1 Cấu Trúc Giao Dịch

InnoDB duy trì hai cấu trúc toàn cục và per-transaction để quản lý giao dịch:

trx_sys (Global)

  • mutex: Kiểm soát critical section cho phân bổ/commit/rollback
  • max_trx_id: Transaction ID tối đa hiện tại
  • trx_list: Danh sách tất cả active transactions
  • view_list: Danh sách tất cả ReadView hiện hành

trx_struct (Per-Transaction)

  • id/no: Transaction ID (id người dùng thấy, no ẩn)
  • xid: XA transaction identifier
  • read_view: ReadView của transaction này
  • trx_locks: Tất cả locks transaction đang giữ
  • wait_lock: Lock đang chờ hiện tại

⚠️ Chi tiết quan trọng về max_trx_id

Transaction ID được phân bổ 256 lần mới ghi một lần ra file để đảm bảo durability. Đây là trade-off giữa performance (giảm I/O) và correctness — nếu crash xảy ra, InnoDB có thể skip tối đa 256 transaction ID, nhưng điều này không ảnh hưởng đến tính đúng đắn vì ID chỉ cần đơn điệu tăng.

2.3 XA Transaction & Group Commit

InnoDB sử dụng XA nội bộ để đảm bảo nhất quán giữa InnoDB redo log và MySQL binlog theo quy trình 2-phase commit:

InnoDB prepare → Binlog commit → InnoDB commit

Binlog đóng vai trò Transaction Coordinator (TC). Hai tham số kiểm soát durability:

  • sync_binlog: Bao nhiêu transaction commit thì fsync binlog (1 = max durability)
  • innodb_flush_log_at_trx_commit: 0/1/2 — kiểm soát flush redo log

✅ Group Commit — Cải tiến quan trọng nhất của MySQL 5.6

Group Commit cho phép nhiều transactions cùng flush binlog một lần, tăng throughput đáng kể trong workload commit nặng. Đây là một trong những tối ưu hóa quan trọng nhất của MySQL 5.6.

2.4 Mini-Transaction (MTR)

Mini-transaction là đơn vị atomic nhỏ nhất trong InnoDB, không phải là giao dịch người dùng. MTR đảm bảo tính nguyên tử cho mỗi thao tác page:

  • Truy cập page → thêm S-latch (đọc) hoặc X-latch (ghi)
  • Sửa page → ghi redo log vào local buffer của MTR
  • Commit MTR → flush redo log vào log buffer + thêm dirty page vào Flush List + giải phóng latch

3.2 Cấu Trúc Row Lock

InnoDB quản lý row lock thông qua hash table toàn cục (lock_sys). Hash key được tính từ [space_id, page_no] — tất cả locks trên cùng một page nằm trong cùng một hash bucket.

💡 Tại sao hash theo page, không phải theo row?

Vì một lock_rec_struct đại diện cho tất cả record locks trên một index page, dùng bitmap để biểu diễn. Thiết kế này tiết kiệm bộ nhớ đáng kể khi có nhiều locks trên cùng một page.

3.3 Các Loại Lock và Semantic

  • S Lock Shared — nhiều transaction cùng đọc
  • X Lock Exclusive — chỉ một transaction ghi
  • IS / IX Intention Lock — báo hiệu ý định lock ở tầng thấp hơn
  • Gap Lock Khóa khoảng giữa các bản ghi (chỉ RR isolation)
  • Next-Key Lock Record Lock + Gap Lock phía trước
  • Insert Intention Lock Gap lock đặc biệt cho INSERT

3.4 Semi-Consistent Read & Implicit Lock

💡 Semi-Consistent Read

Tính năng đặc biệt giúp giảm lock conflict trong RC isolation: khi UPDATE gặp một locked row, InnoDB đọc committed version của row đó để kiểm tra WHERE condition. Nếu row không thỏa mãn điều kiện, bỏ qua ngay mà không cần chờ lock — tối ưu hóa throughput cho UPDATE với nhiều điều kiện filter.

Implicit Lock: InnoDB không thực sự tạo lock object cho mọi bản ghi. Với newly inserted record chưa commit, transaction ID trên record chính là "implicit lock". Chỉ khi transaction khác muốn lock record đó, implicit lock mới được chuyển thành explicit lock. Điều này tiết kiệm bộ nhớ đáng kể.

4. MVCC — Kiểm Soát Đồng Thời Đa Phiên Bản

4.1 ReadView và Cơ Chế Visibility

Mỗi snapshot read tạo một ReadView chứa:

  • low_limit_id: Transaction ID ≥ giá trị này → không thấy (transaction bắt đầu sau snapshot)
  • up_limit_id: Transaction ID < giá trị này → thấy (transaction đã commit trước snapshot)
  • trx_ids: Danh sách active transactions khi tạo snapshot → không thấy

4.2 System Columns Ẩn của InnoDB

InnoDB mở rộng mỗi record trong clustered index với các system columns ẩn:

  • DB_TRX_ID (6 bytes): ID của transaction gần nhất modify record
  • DB_ROLL_PTR (7 bytes): Con trỏ đến undo record trong rollback segment
  • DB_ROW_ID: Row ID tự động nếu không có primary key

✅ Best Practice: RC + Row-Based Binlog

Alibaba và nhiều large-scale MySQL deployments ưa dùng RC + row-based binlog. RC giảm thiểu gap locks, giảm deadlock, tăng concurrency. Chỉ cần đảm bảo dùng row-based binlog để tránh replication issues. RR chỉ nên dùng khi ứng dụng thực sự cần repeatable read semantics.

4.4 Purge — Thu Hồi Phiên Bản Cũ

Purge thread chạy nền, định kỳ thu hồi records có Delete_Bit = 1 mà không còn transaction nào có thể nhìn thấy.

🚨 Long-running Transaction — Kẻ Thù Của Purge

Nếu một transaction mở quá lâu (giữ snapshot cũ), purge thread không thể thu hồi các phiên bản cũ. Điều này dẫn đến: (1) undo tablespace phình to, (2) history list length tăng, (3) query chậm do phải traverse nhiều undo versions. Đây là nguyên nhân phổ biến của "InnoDB undo segment growth" trong production.

5. Tổng Kết và Best Practices

✅ Nên làm

  • Giữ transaction ngắn nhất có thể
  • Dùng RC isolation + row-based binlog cho high-concurrency
  • Monitor SHOW ENGINE INNODB STATUS để theo dõi lock waits
  • Dùng covering index để tận dụng Index Only Scan
  • Tune innodb_purge_threads nếu heavy delete workload

❌ Tránh làm

  • Long-running transactions (ngăn purge, tăng undo size)
  • SELECT ... FOR UPDATE trên full table scan
  • Bỏ qua deadlock detection trong application code
  • Dùng SERIALIZABLE isolation trừ khi thực sự cần
  • AUTO_INCREMENT mode 0 trong high-concurrency insert
