🔐 MySQL: Phân Tích Cơ Chế Khóa Toàn Diện

Hướng dẫn phân tích lock trong MySQL InnoDB: từ nguyên lý đến thực tiễn sản xuất

1. Nền Tảng: 2PL và MVCC

MySQL InnoDB kết hợp hai giao thức đồng thời: MVCC cho Snapshot Read (không cần lock) và 2PL (Two-Phase Locking) cho Current Read (cần lock). Hiểu rõ ranh giới này là chìa khóa để phân tích lock.

Snapshot Read (MVCC, không lock)

  • SELECT thông thường trong RC/RR
  • Đọc phiên bản MVCC phù hợp với ReadView
  • Không thêm bất kỳ lock nào
  • Không bị block bởi write locks

Current Read (2PL, có lock)

  • SELECT ... FOR UPDATE / LOCK IN SHARE MODE
  • INSERT / UPDATE / DELETE
  • Đọc phiên bản mới nhất, thêm lock
  • Có thể bị block bởi conflict locks

2. Các Loại Lock và Ý Nghĩa

2.1 Record Lock

Lock trên một record cụ thể trong index. Luôn lock trên INDEX record, không phải trên bản ghi vật lý. Hai chế độ: S (Shared) lock và X (Exclusive) lock.

2.2 Gap Lock

Lock trên "khoảng trống" giữa các giá trị index, ngăn chặn INSERT vào khoảng đó. Gap lock chỉ tồn tại trong RR isolation để ngăn Phantom Read.

💡 Gap Lock không xung đột với nhau!

Hai transactions có thể cùng giữ Gap Lock trên cùng một khoảng mà không bị block. Gap Lock chỉ xung đột với Insert Intention Lock. Đây là nguyên nhân tại sao Gap Lock có thể gây deadlock một cách bất ngờ.

2.3 Next-Key Lock

Next-Key Lock = Record Lock + Gap Lock phía trước record. Đây là lock type mặc định của InnoDB cho current read trong RR isolation.

-- Bảng t có records: 1, 5, 10, 20
-- SELECT * FROM t WHERE id > 5 FOR UPDATE (RR)
-- Next-Key Locks được đặt:
--   (5, 10]  -- lock record 10 + gap (5,10)
--   (10, 20] -- lock record 20 + gap (10,20)
--   (20, +∞) -- gap lock đến supremum

2.4 Insert Intention Lock

Loại Gap Lock đặc biệt cho INSERT. Nhiều INSERT vào cùng một gap có thể dùng hành (không xung đột với nhau), nhưng bị block nếu có Gap Lock trên khoảng đó.

4. Index Condition Pushdown (ICP) và Lock

ICP (MySQL 5.6+) cho phép storage engine filter records ngay trên index trước khi return về MySQL Server. Điều này có tác động lớn đến số lượng locks được đặt:

  • Trước ICP: Mọi record trong Index Key range phải được lock, dù không thỏa mãn Index Filter
  • Sau ICP: Chỉ lock records thỏa mãn cả Index Key và Index Filter

✅ Best Practice: Luôn Enable ICP

ICP (optimizer_switch='index_condition_pushdown=on') giảm số lượng locks và giảm lock contention, đặc biệt quan trọng với queries có nhiều filter conditions.

5. Semi-Consistent Read — Giảm Lock Conflict

-- Session 1:
UPDATE t SET status='processed' WHERE status='pending' AND region='HN';
-- Session 2 (đồng thời):
UPDATE t SET status='processed' WHERE status='pending' AND region='HCM';
-- Với Semi-Consistent Read (RC):
-- S1 gặp row của S2 với region='HCM' → đọc committed version
-- Thấy region='HCM' != 'HN' → skip, không wait lock!
-- Kết quả: 2 sessions song song, không block nhau

6. Phân Tích WHERE Condition — Bí Quyết Hiểu Lock

💡 Phân Chia WHERE Condition Thành 3 Phần

  • Index Key: Điều kiện xác định scan range trên index
  • Index Filter: Điều kiện có thể check trên index nhưng không là Index Key
  • Table Filter: Điều kiện chỉ check được trên clustered index (full record)
DELETE FROM t1 
WHERE pubtime > 1 AND pubtime < 20  -- Index Key
  AND userid = 'hdc'                  -- Index Filter (nếu có composite index)
  AND comment IS NOT NULL;            -- Table Filter

7. Đọc Lock Info từ INNODB STATUS

SHOW ENGINE INNODB STATUS\G
-- Phần quan trọng:
-- TRANSACTIONS section: liệt kê các transactions đang chờ lock
-- LATEST DETECTED DEADLOCK: thông tin deadlock gần nhất
-- "lock_mode X locks rec but not gap" → Record X Lock
-- "lock_mode X locks gap before rec"  → Gap Lock
-- "lock_mode X"                        → Next-Key Lock
