⚡ RocksDB & MyRocks

LSM Tree Architecture, Write/Read Path, MVCC qua Sequence Numbers, và kinh nghiệm production tại Alibaba — từ 506.8TB InnoDB xuống 76.2TB MyRocks

1. Tổng Quan: Tại Sao Cần LSM Tree?

RocksDB, được Facebook phát triển và open-source từ năm 2013 (fork từ Google LevelDB), đại diện cho một triết lý thiết kế hoàn toàn khác với B-Tree của InnoDB. Câu hỏi cốt lõi là: tại sao lại cần một storage engine khác khi InnoDB đã hoạt động tốt?

⚡ Vấn đề cơ bản của B-Tree với SSD

B-Tree tối ưu cho random read (tìm kiếm O(log n)), nhưng random write trên SSD có vấn đề: SSD phải erase cả block (128KB-4MB) trước khi write, gây ra Write Amplification (WA) rất cao. Mỗi logical write của user có thể dẫn đến hàng chục physical write thực sự lên SSD. LSM Tree giải quyết vấn đề này bằng cách chuyển tất cả write thành sequential append — hiệu quả nhất trên cả HDD lẫn SSD.

1.1 LSM Tree: Ý Tưởng Căn Bản

Log-Structured Merge-tree (LSM Tree) được Patrick O'Neil đề xuất năm 1996. Thay vì sửa dữ liệu tại chỗ (in-place update) như B-Tree, LSM Tree luôn ghi thêm vào cuối (append-only). Dữ liệu ban đầu nằm trong memory (Memtable), sau đó được flush xuống disk thành các file bất biến (SST files), và định kỳ merge lại thành file lớn hơn qua quá trình Compaction.

2. Kiến Trúc RocksDB: Các Tầng Lưu Trữ

RocksDB tổ chức dữ liệu thành nhiều tầng (levels), mỗi tầng lớn hơn tầng trước theo một tỉ lệ cố định (thường là 10x). Đây là thiết kế cốt lõi quyết định toàn bộ tradeoff của hệ thống.

2.1 Cấu Trúc Tầng (Level Structure)

Memtable (RAM)
~64MB, sorted, writable
Level 0 (L0)
4-8 SST files, overlapping keys
Level 1 (L1)
~256MB, non-overlapping, sorted
Level 2 (L2)
~2.5GB, non-overlapping
Level N (Lmax)
Phần lớn dữ liệu, target size = Lmax_size

⚡ Tính chất quan trọng của từng tầng

  • L0: Các SST file có thể có key range chồng lên nhau (overlapping). Đây là điểm đặc biệt — khi read phải check TẤT CẢ L0 files. Khi L0 đầy (>4 files mặc định), compaction được trigger.
  • L1 trở đi: SST files được sắp xếp và không chồng nhau (non-overlapping). Mỗi key chỉ xuất hiện trong đúng một SST file ở mỗi level. Binary search có thể được dùng để tìm đúng file.
  • Compaction: Khi Ln đầy, merge với Ln+1 để tạo ra file mới, xóa version cũ. Đây là quá trình "trả nợ" write amplification.

2.2 SST File (Sorted String Table)

Mỗi SST file là một file bất biến (immutable) chứa dữ liệu đã được sắp xếp theo key. Cấu trúc nội bộ của SST file gồm nhiều lớp để tối ưu read:

Data Blocks

Chứa key-value pairs thực sự, được nén (Snappy/LZ4/Zstd). Mỗi block ~4KB, có checksum riêng.

Index Blocks

Chứa last key của mỗi data block → binary search để tìm đúng block khi lookup. Được cache trong Block Cache.

Filter Blocks (Bloom Filter)

Probabilistic data structure, 10-bit per key, false positive ~1%. Giúp skip SST files không chứa key cần tìm — quan trọng cho read performance.

Metadata Blocks

Statistics, compression dictionary, range deletion tombstones. Footer chứa pointer đến các block khác.

3. Write Path: Từ Client Đến Disk

Write path của RocksDB được thiết kế để đạt throughput cao nhất có thể. Hiểu rõ từng bước giúp giải thích tại sao RocksDB vượt trội về write performance.

Client gọi DB::Put(key, value) — Tạo WriteBatch chứa một hoặc nhiều operations (Put/Delete/Merge)
WAL (Write Ahead Log) — WriteBatch được append vào WAL trước. WAL là sequential log file trên disk. Đảm bảo durability — nếu crash, có thể replay WAL để recover Memtable.
Memtable Insert — Sau khi WAL write thành công, dữ liệu được insert vào Active Memtable (SkipList hoặc HashSkipList). Memtable hoàn toàn trong RAM → write cực nhanh.
Memtable Full → Immutable Memtable — Khi Active Memtable đầy (~64MB), nó trở thành Immutable Memtable (read-only). Active Memtable mới được tạo ngay lập tức để không block writes.
Flush: Immutable → L0 SST — Background thread flush Immutable Memtable xuống disk thành L0 SST file. File này immutable — không bao giờ bị sửa đổi.
Compaction: L0 → L1 → ... → Lmax — Background compaction threads merge SST files từ tầng này sang tầng kế tiếp. Xóa duplicate keys và tombstones, đảm bảo dữ liệu sorted và không chồng nhau ở L1+.

3.1 Write Stall và Backpressure

⚠️ Write Stall: Kẻ Thù Ngầm của RocksDB

Khi compaction không theo kịp write rate, L0 file count tăng vượt ngưỡng. RocksDB sẽ kích hoạt write stall — làm chậm writes của application để compaction có thể bắt kịp. Nếu vẫn không đủ, RocksDB block writes hoàn toàn. Đây là "hidden cost" quan trọng khi vận hành RocksDB trong production — cần monitor rocksdb.stall-time và l0-file-count liên tục.

// Cấu hình để giảm write stall
options.level0_slowdown_writes_trigger = 20;  // default: 20
options.level0_stop_writes_trigger = 36;      // default: 36
options.max_background_jobs = 8;              // tăng compaction threads
options.write_buffer_size = 128 * 1024 * 1024; // 128MB memtable

3.2 Group Commit trong Write Path

RocksDB triển khai cơ chế tương tự Group Commit của MySQL để tăng throughput WAL write. Khi nhiều threads cùng muốn write, RocksDB gộp chúng thành một "write group" — một thread leader viết WAL cho cả nhóm, các threads follower đợi. Điều này giảm số lần fsync và tăng throughput đáng kể khi có nhiều concurrent writers.

4. Read Path: Point Lookup và Range Scan

Read path phức tạp hơn write path vì dữ liệu có thể nằm ở nhiều tầng khác nhau — thậm chí cùng một key có thể xuất hiện ở Memtable, L0, L1, L2 với các version khác nhau. RocksDB phải tìm version mới nhất với sequence number cao nhất.

4.1 Point Lookup (Tìm Một Key)

👉 [CHÈN ẢNH: Read path diagram — từ Memtable xuống L0, L1, L2, với Bloom Filter check ở mỗi bước]
Active Memtable — Check SkipList. O(log n). Nếu tìm thấy và là version mới nhất, return ngay.
Immutable Memtables — Check từng Immutable Memtable theo thứ tự mới → cũ. Thường chỉ 1-2 Immutable Memtables.
L0 SST Files — Check TẤT CẢ L0 files (vì keys có thể chồng nhau). Bloom Filter được check trước để skip files không chứa key. Bloom Filter miss rate ~1%.
L1, L2, ... Lmax — Vì non-overlapping, chỉ cần binary search để tìm đúng 1 SST file ở mỗi level. Bloom Filter kiểm tra → nếu có, load data block từ Block Cache hoặc disk.
Block Cache — Data blocks được cache trong RAM (Block Cache, thường 1-8GB). Cache hit = không cần disk I/O. LRU eviction policy.

❌ Write Amplification vs Read Amplification: Tradeoff Cơ Bản

LSM Tree có Read Amplification cao hơn B-Tree: một point lookup có thể phải check nhiều levels. Với Bloom Filter tốt, thực tế thường chỉ đọc 1-2 files. Nhưng worst case (key không tồn tại) phải check tất cả levels. Đây là tradeoff căn bản: LSM Tree đổi write efficiency cao lấy read efficiency thấp hơn một chút.

4.2 Range Scan (Iterator)

Range scan phức tạp hơn point lookup vì phải merge kết quả từ nhiều sources khác nhau theo thứ tự key.

Iterator Hierarchy

DBIter (Top Level)

Interface bên ngoài. Ẩn MVCC — chỉ return version visible cho snapshot hiện tại. Gọi MergingIterator bên dưới.

MergingIterator

Merge nhiều sorted streams lại. Dùng min-heap để luôn return key nhỏ nhất tiếp theo. O(log k) mỗi next() call, k = số iterators.

MemtableIterator

Iterator trên SkipList của Memtable. Forward scan rất nhanh nhờ linked list structure của SkipList.

TwoLevelIterator (SST)

Index block → data block. Khi reach cuối một data block, đọc next block. Lazy loading — chỉ load block khi cần.

Fractional Cascading — Tối Ưu Range Scan

Fractional Cascading là kỹ thuật từ computational geometry giúp tăng tốc binary search khi tìm cùng một key trong nhiều sorted lists. Thay vì binary search độc lập trong từng level (O(k log n)), Fractional Cascading giảm xuống O(log n + k) bằng cách "cascade" thông tin vị trí từ level này sang level kế tiếp.

💡 Tại Sao Fractional Cascading Quan Trọng Cho Range Scan?

Trong range scan, khi ta đã tìm thấy key K ở Level 1 tại vị trí p1, thì ở Level 2 key K phải nằm trong một range có thể suy ra từ p1. Không cần binary search lại từ đầu. Điều này đặc biệt có lợi khi scan qua nhiều keys liên tiếp — hầu hết các lần seek kế tiếp chỉ cần một vài comparisons thay vì log(n).

5. MVCC Qua Sequence Numbers

RocksDB triển khai MVCC theo cách đơn giản và thanh lịch hơn InnoDB: mỗi key-value pair được gắn một Sequence Number — một số nguyên tăng dần, global, monotonic.

5.1 Internal Key Format

// Mỗi entry trong RocksDB thực sự có dạng:
Internal Key = user_key + sequence_number + value_type
// value_type: kTypeValue (put) hoặc kTypeDeletion (tombstone)

// Ví dụ:
user_key="alice" seq=100 type=kTypeValue   → value="alice@corp.com"
user_key="alice" seq=50  type=kTypeValue   → value="alice@gmail.com"
user_key="alice" seq=10  type=kTypeDeletion → (deleted)

Các entries được sắp xếp theo thứ tự: user_key ASC, sequence_number DESC. Nghĩa là với cùng một user_key, version mới nhất (sequence number cao nhất) luôn xuất hiện trước. Khi read, RocksDB tìm version đầu tiên có sequence number ≤ snapshot's sequence number.

5.2 Snapshot Isolation

Snapshot Creation

Gọi DB::GetSnapshot() → return current sequence number. Chi phí O(1), không copy data.

Read With Snapshot

Iterator chỉ thấy entries với seq ≤ snapshot_seq. Đảm bảo consistent read tại một thời điểm.

Garbage Collection

Compaction xóa versions không còn cần thiết — versions cũ hơn oldest snapshot. Đây là lý do phải monitor snapshot count.

No Undo Log

Khác InnoDB, RocksDB không có undo log riêng. Old versions nằm ngay trong data files — đơn giản hơn nhưng GC phụ thuộc vào compaction schedule.

⚠️ Snapshot Leak: Vấn Đề Phổ Biến Trong Production

Nếu application giữ một snapshot lâu (quên release), compaction không thể xóa old versions. Dữ liệu tích lũy ngày càng nhiều. Monitor rocksdb.num-snapshots và rocksdb.oldest-snapshot-time. Đây là nguồn gốc phổ biến của hiện tượng "RocksDB grow without bound" trong production.

6. MyRocks: RocksDB Làm Storage Engine Cho MySQL

MyRocks là dự án tích hợp RocksDB làm storage engine thay thế InnoDB trong MySQL. Được phát triển bởi Facebook và sau đó được Alibaba adopt vào AliSQL/PolarDB-X.

6.1 Kiến Trúc MyRocks

👉 [CHÈN ẢNH: MySQL layer → MySQL SE API → MyRocks handler → RocksDB library → SST files trên disk]

MyRocks implement MySQL Storage Engine API — cùng interface mà InnoDB dùng. MySQL server (parser, optimizer, replication) không cần thay đổi. Chỉ tầng storage engine được swap.

6.2 Key Encoding trong MyRocks

Một thách thức lớn khi dùng RocksDB (key-value store) làm backend cho MySQL (relational database) là encoding dữ liệu. MyRocks phải encode cả clustered index và secondary indexes vào format key-value.

-- InnoDB: clustered index key = primary key
-- MyRocks: clustered index key = table_id + primary_key_columns
-- Encoded theo Memcomparable format để sort đúng

-- Secondary index trong MyRocks:
-- Key   = table_id + index_id + index_columns + primary_key
-- Value = (rỗng, vì primary key đã trong key)

-- Ví dụ: table users(id INT, name VARCHAR, email VARCHAR), PK=id, INDEX(name)
-- Clustered: key="\x00\x01" + encode(id), value=encode(name)+encode(email)
-- Secondary: key="\x00\x02" + encode(name) + encode(id), value=""

💡 Memcomparable Encoding

MySQL có nhiều kiểu dữ liệu với sort order phức tạp (VARCHAR có collation, DECIMAL có dấu). MyRocks phải encode chúng thành byte sequences mà khi so sánh byte-by-byte sẽ cho kết quả đúng. Đây gọi là "memcomparable format" — encode một lần để RocksDB's natural byte comparison tự động xử lý sort order đúng.

6.3 Transaction Support

MyRocks dùng RocksDB's OptimisticTransaction hoặc PessimisticTransaction để implement MySQL transactions. Optimistic transactions không hold locks khi read, chỉ validate at commit time — phù hợp với workload ít conflicts.

7. Kinh Nghiệm Production Tại Alibaba

Alibaba deploy MyRocks cho một số workloads quan trọng, với kết quả ấn tượng nhưng cũng nhiều bài học đắt giá.

7.1 Kết Quả Nén Storage

Metric InnoDB MyRocks Cải thiện
Storage dùng 506.8 TB 76.2 TB 6.6x nhỏ hơn
Compression ratio ~1.3x (InnoDB compressed) ~8.5x Vượt trội
Write throughput Baseline +30-50% Tốt hơn
Read throughput (point) Baseline -20 đến -40% Kém hơn
Read throughput (range) Baseline -30 đến -60% Kém hơn đáng kể
CPU usage Baseline +10-20% (compaction) Cao hơn một chút

✅ Workload Phù Hợp Với MyRocks

  • Write-heavy workloads: Logging, event streaming, time-series data
  • High compression ratio: Data có tính lặp cao (user events, transactions history)
  • Cost-sensitive: Storage cost chiếm phần lớn OPEX, sẵn sàng đánh đổi read performance
  • Cold data: Data ít được read nhưng cần lưu lâu dài

❌ Workload Không Phù Hợp

  • OLTP read-heavy: E-commerce product catalog, user profile lookup — read latency quan trọng hơn storage cost
  • Complex joins với range scans: MyRocks range scan kém InnoDB đáng kể
  • Full-text search: Không được optimize cho MyRocks
  • Latency-sensitive: Write stall có thể gây latency spike không chấp nhận được

7.2 Bài Học Production Quan Trọng

Bài Học 1: Compaction Tuning Rất Phức Tạp

Compaction có hàng chục parameters và không có "one size fits all". Alibaba phải điều chỉnh compaction_readahead_size, max_background_compactions, target_file_size_base, max_bytes_for_level_base cho từng cluster riêng. Sai một tham số có thể gây write stall hoặc read amplification tăng đột ngột.

Bài Học 2: Monitoring Khác InnoDB Hoàn Toàn

Các metrics quan trọng cần monitor trong MyRocks khác hoàn toàn InnoDB:

-- RocksDB metrics cần monitor:
rocksdb.block-cache-hit-count     -- Block cache effectiveness
rocksdb.bloom-filter-useful       -- Bloom filter tỉ lệ skip
rocksdb.compaction-pending        -- Compaction queue depth
rocksdb.num-files-at-level{N}    -- L0 file count (write stall indicator)
rocksdb.stall-time               -- Tổng thời gian bị write stall
rocksdb.write-amplification      -- WA = bytes_written_to_disk / bytes_from_client

Bài Học 3: Backup Phức Tạp Hơn

InnoDB có --backup mode với Percona XtraBackup. MyRocks cần myrocks_hotbackup — backup logic khác hoàn toàn vì SST files immutable. Checkpoint API giúp tạo snapshot nhất quán, nhưng tooling ecosystem chưa mature bằng InnoDB.

Bài Học 4: DDL Operations Chậm Hơn

ALTER TABLE trên MyRocks thường chậm hơn InnoDB vì phải rebuild toàn bộ SST files. Online DDL support còn hạn chế. Cần lên kế hoạch schema changes kỹ lưỡng hơn.

8. So Sánh LSM Tree vs B-Tree: Tradeoff Toàn Diện

Dimension B-Tree (InnoDB) LSM Tree (RocksDB) Ghi Chú
Write Amplification 3-10x (B-Tree update) 10-30x (Compaction) LSM WA phụ thuộc nhiều vào workload
Read Amplification 2-4x (buffer pool miss) 3-10x (multi-level check) Bloom filter giảm đáng kể
Space Amplification 2-3x (page fragmentation) 1.1-1.5x (sau compaction) LSM vượt trội về space
Write Latency Predictable Variable (write stall risk) InnoDB ổn định hơn
Compression Trung bình (per-page) Tốt (per-block, dictionary) LSM compress tốt hơn nhiều
SSD Friendliness Trung bình (random write) Tốt (sequential write) LSM tốt hơn cho SSD longevity
Range Scan Tốt (sequential read) Trung bình (merge overhead) InnoDB tốt hơn cho OLAP
Backup Complexity Thấp (XtraBackup) Cao (custom tooling) InnoDB ecosystem mature hơn

9. Kết Luận: Khi Nào Chọn MyRocks?

MyRocks/RocksDB không phải "InnoDB tốt hơn" — đó là một tradeoff khác. Để quyết định đúng:

Chọn MyRocks khi:

  • Write throughput > Read throughput trong workload
  • Storage cost là vấn đề lớn (6x savings đáng kể)
  • Data cold/warm ratio cao (nhiều data ít được đọc)
  • SSD longevity quan trọng (ít random write hơn)

Giữ InnoDB khi:

  • Read-heavy OLTP (point lookups chiếm đa số)
  • Latency SLA nghiêm ngặt (write stall không chấp nhận)
  • Complex queries với range scans và joins
  • Team chưa có kinh nghiệm RocksDB tuning

✅ Kết Luận Thực Tiễn Từ Alibaba

Alibaba sử dụng cả hai song song: InnoDB cho OLTP hot data (đơn hàng, inventory, user sessions), MyRocks cho cold data (lịch sử giao dịch, logs, audit trails). Chiến lược "tiered storage" này tối ưu cả performance lẫn cost. Không phải "all-in" vào một engine — biết rõ tradeoffs của từng engine và dùng đúng tool cho đúng job là chìa khóa.
