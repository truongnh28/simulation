⚡ MVCC: Oracle vs InnoDB vs PostgreSQL

So sánh chuyên sâu ba cách triển khai Multiversion Concurrency Control trong các hệ quản trị cơ sở dữ liệu hàng đầu

1. MVCC Là Gì và Tại Sao Cần Nó?

MVCC (Multi-Version Concurrency Control) là kỹ thuật cho phép nhiều transactions đọc/ghi dữ liệu đồng thời mà không block lẫn nhau. Thay vì dùng exclusive lock cho mọi thao tác, MVCC duy trì nhiều phiên bản của cùng một dữ liệu.

Ưu điểm MVCC

  • Đọc không block ghi, ghi không block đọc
  • Concurrency cao hơn Lock-Based CC
  • OLTP workload 80% đọc → tối ưu
  • Snapshot isolation tự nhiên

Thách thức MVCC

  • Quản lý phiên bản cũ (garbage collection)
  • Tốn thêm không gian lưu trữ
  • Overhead khi xác định visibility
  • Long-running transactions gây bloat

2. Oracle MVCC — Timestamp-Based, Page-Level

2.1 Cơ Chế SCN (System Change Number)

Oracle dùng SCN — một số nguyên tăng đơn điệu — làm logical timestamp cho toàn hệ thống. SCN mới được tạo ra mỗi khi một transaction commit.

  • Format: 0xFFFF.FFFFFFF (6 bytes)
  • Chuyển đổi: SELECT scn_to_timestamp(SCN) FROM dual
  • Đảm bảo thứ tự toàn cục của mọi thay đổi

2.2 Page-Level Multi-Version với Rollback Segment

Oracle dùng page-level versioning: khi cần đọc phiên bản cũ, Oracle undo toàn bộ page (không phải từng row riêng lẻ) về trạng thái tại SCN cho trước.

Cấu trúc Oracle Data Block gồm 3 layer: Cache layer (20 bytes header: rdba, scn, seq), Transaction layer (Fixed: ITL count, Variable: ITLs), Data layer (Row directory, Row data)

2.3 ITL (Interested Transaction List)

Mỗi Oracle data block có một ITL — danh sách các transactions đang/đã thao tác trên block đó:

  • INITRANS: Số ITL slots ban đầu (mặc định 1 cho data, 2 cho index)
  • MAXTRANS: Số ITL slots tối đa
  • Transaction ID format: xid: 0x0004.00e.0000449b (rollback segment number : slot : wrap count)

2.4 Block Cleanout

Sau khi transaction commit, Oracle phải "làm sạch" block — cập nhật ITL, thiết lập SCN, xóa row lock marks. Có hai cơ chế:

  • Fast Block Cleanout: Commit ngay lập tức làm sạch các blocks đã cache (giới hạn số lượng)
  • Deferred Block Cleanout: Blocks không được làm sạch ngay; khi transaction khác đọc block, nó sẽ làm sạch theo cách lazy

💡 Tại sao cần Deferred Cleanout?

Commit một transaction lớn cần làm sạch hàng ngàn blocks sẽ tốn nhiều thời gian nếu thực hiện đồng bộ. Deferred cleanout trải đều công việc này ra theo thời gian, giảm latency commit. Đây là ví dụ điển hình của trade-off: commit nhanh hơn nhưng read đầu tiên sau commit chậm hơn một chút.

2.5 Ora-01555: Snapshot Too Old

Lỗi nổi tiếng nhất của Oracle MVCC: khi undo segments bị overwrite trước khi query hoàn thành việc đọc phiên bản cũ.

  • Nguyên nhân: UNDO_RETENTION quá nhỏ, undo tablespace quá nhỏ, hoặc long-running query
  • Giải pháp: Tăng undo_retention, dùng Automatic Undo Management
  • Oracle hỗ trợ Flashback Query: SELECT ... AS OF TIMESTAMP ... — truy vấn dữ liệu tại thời điểm trong quá khứ

2.6 Phân Tích Ưu/Nhược Điểm Oracle MVCC

✅ Ưu điểm

  • Không lưu version info trong record — tiết kiệm row overhead
  • Hỗ trợ Flashback Query mạnh mẽ
  • CR Block (Consistent Read Block) tái sử dụng được

❌ Nhược điểm

  • Page-level undo gây "false violation" — nhiều readers cùng cần undo cùng page
  • Ora-01555 trong long-running queries
  • Full table scan song song cần hint: SELECT /*+parallel(t 8)*/ ...

3. InnoDB MVCC — Transaction ID-Based, Row-Level

3.1 System Columns Ẩn trong Clustered Index

-- Mỗi InnoDB record có các hidden columns:
DB_TRX_ID (6 bytes)     -- Transaction ID tạo/sửa record
DB_ROLL_PTR (7 bytes)   -- Con trỏ đến undo record
-- DB_ROLL_PTR format:
-- bit[0]: Undo type (Insert=0, Update=1)
-- bits[1-7]: Rollback Segment ID (128 segments)
-- bits[8-39]: Undo Page Number
-- bits[40-55]: Offset trong Undo Page

3.2 Update/Delete Handling

OperationClustered IndexSecondary Index
DELETESet Delete_Bit, ghi undo với full recordSet Delete_Bit (không ghi undo)
UPDATE (key thay đổi)In-place update, undo chứa before-imageClone mới + Delete_Bit record cũ
UPDATE (key không đổi)In-place update, undo chứa before-imageKhông thay đổi

3.3 ReadView Visibility Algorithm

-- Pseudocode kiểm tra visibility của record có trx_id:
function is_visible(trx_id, read_view):
    if trx_id < read_view.up_limit_id:
        return TRUE   -- Committed trước snapshot
    if trx_id >= read_view.low_limit_id:
        return FALSE  -- Bắt đầu sau snapshot
    if trx_id in read_view.trx_ids:
        return FALSE  -- Đang active khi tạo snapshot
    return TRUE       -- Committed trước snapshot

3.4 Phân Tích Ưu/Nhược Điểm InnoDB MVCC

✅ Ưu điểm

  • Row-level versioning — không có false violation
  • Đơn giản hơn Oracle về mặt conceptual
  • Purge độc lập với query path

❌ Nhược điểm

  • Record overhead tăng (system columns)
  • Không thể xóa vật lý ngay (cần purge)
  • Undo cần lưu tất cả secondary index columns
  • Purge performance kém với heavy write
  • Không hỗ trợ Flashback Query

4. PostgreSQL MVCC — Row-Level, In-Page Storage

4.1 Thiết Kế Độc Đáo: Không Có Rollback Segment

PostgreSQL lưu TẤT CẢ phiên bản của record trực tiếp trong heap page, không dùng rollback segment riêng. Một UPDATE tạo ra 2 versions nằm trong cùng (hoặc gần) cùng page.

4.2 System Columns của PostgreSQL

ColumnÝ nghĩa
xminTransaction ID tạo record (INSERT/UPDATE tạo version mới)
xmaxTransaction ID xóa/thay thế record (DELETE/UPDATE/Row Lock)
cminCommand ID trong cùng transaction (thứ tự statement)
cmaxTương tự cmin nhưng cho DELETE — dùng chung column với cmin

4.3 Vacuum — Garbage Collection của PostgreSQL

PostgreSQL cần VACUUM để thu hồi không gian từ dead tuples:

  • Page-level vacuum: Thu hồi khi page được access
  • Table-level autovacuum: Background process tự động
  • Manual VACUUM: VACUUM ANALYZE table_name

⚠️ Table Bloat — Vấn Đề Kinh Điển của PostgreSQL

Nếu autovacuum không đủ nhanh (heavy write workload), dead tuples tích lũy làm table "bloat" — bảng chiếm nhiều disk space hơn dữ liệu thực. Giải pháp: VACUUM FULL (lock table) hoặc dùng pg_repack extension để rebuild không cần lock.

4.4 Phân Tích Ưu/Nhược Điểm PostgreSQL MVCC

✅ Ưu điểm

  • Implementation đơn giản (không cần rollback segment infrastructure)
  • Phiên bản cũ gần về mặt vật lý → ít random I/O khi rollback
  • Visibility check đơn giản hơn

❌ Nhược điểm

  • Table bloat nếu vacuum không kịp
  • Tốn space: dead tuples chiếm không gian trong page
  • Vacuum là performance hotspot
  • Không hỗ trợ Flashback Query
