👁️ InnoDB MVCC Visibility

Cơ chế nhìn thấy dữ liệu trong InnoDB: row structure, DATA_TRX_ID, ROLL_PTR, Read View (low_limit_id / up_limit_id / trx_ids), clustered vs secondary index visibility, và Purge flow

1. MVCC Là Gì Và Tại Sao Cần Nó?

Multi-Version Concurrency Control (MVCC) là kỹ thuật cho phép nhiều transactions đọc và ghi dữ liệu đồng thời mà không cần block lẫn nhau. Thay vì "chỉ có một version của mỗi row", MVCC duy trì nhiều versions của cùng một row — mỗi transaction thấy version phù hợp với thời điểm nó bắt đầu.

💡 Tại Sao Không Dùng Lock Đơn Giản?

Lock-based concurrency: Reader phải đợi Writer hoàn thành (S lock conflicts with X lock). Với MVCC: Reader đọc version cũ hơn — không bao giờ block Writer và ngược lại. InnoDB's MVCC đảm bảo: SELECT không bao giờ block INSERT/UPDATE/DELETE và ngược lại (trừ khi dùng SELECT FOR UPDATE/SHARE). Đây là nền tảng của "high concurrency" trong MySQL.

2. Cấu Trúc Row Trong InnoDB

Mỗi row trong InnoDB clustered index (B-Tree page) chứa không chỉ data columns của user mà còn thêm các system columns mà người dùng không thấy trực tiếp.

2.1 System Columns Ẩn

Physical row trong InnoDB clustered index page:
user_col_1 user_col_2 ... user_col_N DB_ROW_ID (6B) DB_TRX_ID (6B) DB_ROLL_PTR (7B)
Column Size Ý Nghĩa Ghi Chú
DB_ROW_ID 6 bytes Auto-generated row ID nếu không có PK Chỉ tồn tại khi không có explicit PK
DB_TRX_ID 6 bytes Transaction ID của lần cuối cùng tạo/sửa row Luôn tồn tại, key cho MVCC visibility
DB_ROLL_PTR 7 bytes Pointer vào undo log — chứa version trước của row Tạo thành linked list versions

2.2 Undo Log Chain (Version Chain)

Mỗi khi một row bị UPDATE, InnoDB:

  1. Copy version hiện tại vào undo log (rollback segment)
  2. Cập nhật DB_TRX_ID của row thành transaction ID hiện tại
  3. Set DB_ROLL_PTR trỏ vào undo log entry vừa tạo
👉 [CHÈN ẢNH: Version chain — current row với TRX_ID=100, ROLL_PTR → undo_entry(TRX_ID=80) → undo_entry(TRX_ID=50) → undo_entry(TRX_ID=20) → NULL (original insert)]
-- Giả sử row "Alice" bị update 3 lần:

-- Current (in B-Tree page):
-- user_id=1, name='Alice', salary=90000
-- DB_TRX_ID=100, DB_ROLL_PTR → undo[100]

-- undo[100]: (được tạo khi trx 100 update)
-- name='Alice', salary=80000  (giá trị TRƯỚC khi trx 100 update)
-- DB_TRX_ID=80, DB_ROLL_PTR → undo[80]

-- undo[80]:
-- name='Alice', salary=70000
-- DB_TRX_ID=50, DB_ROLL_PTR → undo[50]

-- undo[50]:
-- name='Alice', salary=60000
-- DB_TRX_ID=20, DB_ROLL_PTR → NULL  (insert gốc)

3. Read View: Quy Tắc Nhìn Thấy

Read View là snapshot của trạng thái transaction system tại thời điểm SELECT bắt đầu (hoặc transaction bắt đầu với REPEATABLE READ). Read View chứa 3 thông tin cốt lõi:

low_limit_id (aka m_low_limit_id)

Transaction ID tiếp theo sẽ được cấp phát = max_trx_id + 1. Mọi row với DB_TRX_ID ≥ low_limit_id KHÔNG ĐƯỢC THẤY — transaction đó bắt đầu sau khi Read View được tạo.

up_limit_id (aka m_up_limit_id)

Transaction ID nhỏ nhất trong list active transactions. Mọi row với DB_TRX_ID < up_limit_id ĐƯỢC THẤY — transaction đó đã commit trước khi Read View được tạo.

trx_ids (aka m_ids)

List tất cả transaction IDs đang active (chưa commit) lúc Read View được tạo. Rows được tạo bởi các transactions này KHÔNG ĐƯỢC THẤY.

creator_trx_id

Transaction ID của transaction tạo Read View này. Rows được tạo bởi chính transaction này LUÔN ĐƯỢC THẤY (transaction thấy changes của chính mình).

3.1 Thuật Toán Visibility Check

// Cho một row với DB_TRX_ID = trx_id:
function is_visible(trx_id, read_view):

    // Rule 1: Chính mình luôn thấy
    if trx_id == read_view.creator_trx_id:
        return VISIBLE

    // Rule 2: Trước tất cả active transactions → đã commit → thấy
    if trx_id < read_view.up_limit_id:
        return VISIBLE

    // Rule 3: Sau khi Read View được tạo → chưa bắt đầu → không thấy
    if trx_id >= read_view.low_limit_id:
        return NOT_VISIBLE

    // Rule 4: Trong range [up_limit_id, low_limit_id):
    // Kiểm tra có trong active list không
    if trx_id in read_view.trx_ids:
        return NOT_VISIBLE  // Vẫn đang active lúc Read View được tạo
    else:
        return VISIBLE      // Đã commit trước Read View được tạo

3.2 Ví Dụ Minh Họa

Timeline:

t=1
Trx 10 START
→
t=2
Trx 20 START
UPDATE Alice salary=90K
→
t=3
Trx 10 SELECT Alice
Read View created
→
t=4
Trx 20 COMMIT
→
t=5
Trx 10 SELECT Alice
(REPEATABLE READ)

Read View của Trx 10 tại t=3:

  • up_limit_id = 10 (Trx 10 là active transaction nhỏ nhất)
  • low_limit_id = 21 (next trx ID sẽ cấp phát)
  • trx_ids = {20} (Trx 20 đang active lúc Read View được tạo)
  • creator_trx_id = 10

Visibility check cho row Alice (DB_TRX_ID = 20, salary = 90K):

  • trx_id(20) ≥ up_limit_id(10) → không thể apply Rule 2
  • trx_id(20) < low_limit_id(21) → không apply Rule 3
  • trx_id(20) ∈ trx_ids{20} → NOT VISIBLE

→ InnoDB follow ROLL_PTR xuống undo log để tìm version trước đó (salary = 80K, DB_TRX_ID = old_trx). Nếu old_trx < 10 → VISIBLE → return salary=80K.

Tại t=5 (REPEATABLE READ): cùng Read View! Dù Trx 20 đã commit, Trx 10 vẫn thấy salary=80K.

4. Clustered Index vs Secondary Index Visibility

Clustered index và secondary index có cơ chế visibility khác nhau — đây là một trong những điểm tinh tế nhất của InnoDB MVCC.

4.1 Clustered Index: Full Information

Mỗi row trong clustered index có đầy đủ DB_TRX_ID và DB_ROLL_PTR. Visibility check trực tiếp và traverse undo chain nếu cần.

4.2 Secondary Index: Chỉ Có MAX_TRX_ID

Secondary index pages không có DB_TRX_ID per-row. Thay vào đó, mỗi secondary index page có một PAGE_MAX_TRX_ID — transaction ID cao nhất đã modify bất kỳ row nào trên page đó.

⚠️ Secondary Index Visibility: Phức Tạp Hơn

Khi đọc từ secondary index, InnoDB phải:

  1. Check PAGE_MAX_TRX_ID. Nếu PAGE_MAX_TRX_ID < up_limit_id → tất cả rows trên page đều visible → không cần lookup clustered index
  2. Nếu PAGE_MAX_TRX_ID ≥ up_limit_id → không chắc → phải lookup clustered index để verify visibility

Điều này tạo ra overhead: covering index scan vẫn có thể phải lookup clustered index (ngăn "covering index optimization" trong trường hợp này).

-- Ví dụ: Table users(id, name, email), INDEX(name)
-- Query: SELECT name, email FROM users WHERE name = 'Alice'
--        (name + email không cover all columns → phải lookup clustered)

-- Nhưng dù có covering index:
-- SELECT name FROM users WHERE name = 'Alice'
-- Nếu PAGE_MAX_TRX_ID >= read_view.up_limit_id → vẫn phải lookup clustered!
-- Đây là "secondary index visibility check" overhead

-- Đây là lý do tại sao trong MVCC heavy workloads,
-- covering index không luôn luôn "cover" như expected

4.3 Purge và Index Cleaning

Khi purge thread dọn dẹp undo log records, nó cũng phải clean secondary index entries cho delete-marked rows. Quá trình:

  1. Purge coordinator xác định undo log records có thể xóa (below low water mark)
  2. Với mỗi DELETE record: tìm secondary index entries tương ứng và remove delete marks
  3. Update PAGE_MAX_TRX_ID nếu row bị purge là row mới nhất trên page
👉 [CHÈN ẢNH: Secondary index page với PAGE_MAX_TRX_ID, và clustered index lookup flow khi MAX_TRX_ID cao]

5. Read View Trong REPEATABLE READ vs READ COMMITTED

Isolation Level Read View Được Tạo Khi Nào? Hệ Quả
REPEATABLE READ (default) Khi transaction thực hiện SELECT đầu tiên Tất cả SELECTs trong transaction dùng cùng một Read View → không thấy changes commit từ transactions khác sau đó
READ COMMITTED Mỗi SELECT statement Mỗi SELECT tạo Read View mới → thấy changes đã committed ngay trước SELECT đó (non-repeatable reads có thể xảy ra)

💡 REPEATABLE READ Không Ngăn Hoàn Toàn Phantom Reads?

MVCC REPEATABLE READ ngăn Non-Repeatable Reads (cùng row đọc lại thấy giá trị khác). Nhưng trong InnoDB, nó cũng ngăn Phantom Reads cho SELECT ... (snapshot read) — bạn không thấy rows mới được insert bởi transactions khác. Tuy nhiên, SELECT FOR UPDATE / SELECT FOR SHARE là current read (locking read) — không dùng Read View, đọc version mới nhất và có thể thấy phantoms. Đây là điểm mà nhiều developer nhầm lẫn.

6. Current Read vs Snapshot Read

Đây là phân biệt quan trọng nhất để hiểu đầy đủ InnoDB MVCC:

Snapshot Read (Non-Locking)

  • SELECT ... FROM ...
  • Dùng Read View → thấy version tương ứng với thời điểm Read View được tạo
  • Không lấy lock
  • Không block writes
  • MVCC provides isolation

Current Read (Locking)

  • SELECT ... FOR UPDATE
  • SELECT ... FOR SHARE
  • INSERT / UPDATE / DELETE
  • Đọc version HIỆN TẠI (mới nhất)
  • Lấy lock (S hoặc X)
  • Có thể thấy phantom rows
-- Kịch bản minh họa (REPEATABLE READ):
-- Session A bắt đầu transaction, đọc users count = 100
BEGIN;
SELECT COUNT(*) FROM users;  -- snapshot read → 100

-- Session B insert 5 users và commit
INSERT INTO users ... ; COMMIT;

-- Session A đọc lại với snapshot read → vẫn 100 (MVCC!)
SELECT COUNT(*) FROM users;  -- 100 (không thấy Session B's inserts)

-- Session A đọc với current read → 105!
SELECT COUNT(*) FROM users FOR UPDATE;  -- 105 (thấy committed changes)

7. Purge: Dọn Dẹp Undo Log

Purge là quá trình background dọn dẹp undo log records và secondary index entries không còn cần thiết nữa. Đây là critical process ảnh hưởng đến performance và disk space.

7.1 Điều Kiện Purge

Một undo log record có thể bị purge khi:

  • Transaction tạo ra nó đã committed
  • Không có active Read View nào cần version đó nữa
  • Cụ thể: trx_id ≤ oldest_active_read_view.up_limit_id

7.2 Purge Flow Chi Tiết

Purge Coordinator scan history list — trx_sys→history_list là linked list các undo log segments, sorted theo commit order. Coordinator đọc từ đầu list (oldest committed first).
Xác định "purge view" — Tìm low_limit_id của oldest active Read View. Chỉ purge records với commit_trx_id < low_limit_id.
Phân phối work cho purge workers — Coordinator gửi undo log records cần purge cho N-1 worker threads. Workers xử lý song song.
Worker purge undo records — Với mỗi UPDATE undo record: free undo log entry. Với DELETE undo record: xóa row từ clustered index và clean secondary index entries.
Update history list — Sau khi purge xong một undo log segment, coordinator xóa nó khỏi history list. Undo tablespace space được reclaimed.

❌ Long-Running Transactions: Kẻ Thù Của Purge

Nếu có một transaction mở từ 1 giờ trước, Read View của nó có up_limit_id thấp. Purge không thể xóa bất kỳ undo record nào newer hơn thời điểm đó — dù hàng triệu transactions khác đã commit. History list tăng vô tận, disk space cạn, và MVCC visibility check ngày càng chậm (phải traverse undo chain dài hơn). Đây là lý do cần monitor và alert khi có long-running transactions.

8. Monitoring MVCC Health

-- Kiểm tra history list length (key metric!):
SHOW ENGINE INNODB STATUS\G
-- Tìm: "History list length 123456"
-- > 10000: cảnh báo, purge lag sau
-- > 100000: nghiêm trọng, cần tìm long-running transactions

-- Tìm long-running transactions:
SELECT trx_id, trx_started, trx_state, trx_query,
       TIMESTAMPDIFF(SECOND, trx_started, NOW()) AS age_seconds
FROM information_schema.INNODB_TRX
WHERE TIMESTAMPDIFF(SECOND, trx_started, NOW()) > 60
ORDER BY age_seconds DESC;

-- Monitor purge lag:
SELECT variable_name, variable_value
FROM performance_schema.global_status
WHERE variable_name IN (
    'Innodb_purge_trx_id_age',
    'Innodb_history_list_length'
);

✅ Best Practices Cho MVCC Health

  • Commit transactions sớm nhất có thể — đặc biệt read-only transactions (dùng SET autocommit=1 hoặc explicit BEGIN/COMMIT)
  • Monitor history list length — alert khi >10K, investigate khi >50K
  • Tăng innodb_purge_threads trên write-heavy servers (4-8 threads)
  • Tránh BEGIN và để transaction "treo" trong application code — connection timeout hay application crash để lại orphan transactions
  • Read Committed isolation tốt hơn cho OLAP queries — Read View mới mỗi statement, không giữ old snapshots lâu
